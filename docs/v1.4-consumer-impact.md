# V1.4：调用方影响验证与可重跑回归包

本地源码版本：1.4.0，2026-11-02。新增能力已接入核心库、Web、API、命令行、导出和历史记录；不代表已经推送或发布。

## 解决什么问题

规范差异只能告诉团队“哪些契约发生了变化”。发布负责人还需要知道：移动端、后台任务、合作方分别依赖哪些交互；已有请求是否被新约束拒绝；新响应是否仍满足调用方实际依赖；应该找谁修改，以及如何重验。

例如，订单规范一直将 `receiptUrl` 声明为可选。新旧 OpenAPI 完全一样，但新版实际响应样例不再包含这个地址，而移动端进入收据页面时必须读取它。静态 diff 没有规范变化可报告。V1.4 允许移动端提交独立的响应断言与前后样例，指出该样例不满足调用方要求，并保留检查 ID、失败位置、负责人和迁移任务。

这里的“实际依赖”来自调用方提供的声明，系统不会自动扫描客户端代码，也不会证明提交的样例来自线上。它是**静态契约分析 + 调用方样例验证**，不是自动发布 Agent、线上抓包平台或完整契约测试服务。与成熟工具的实跑对照及边界见 [能力范围对照](v1.4-engine-comparison.md)。

## 马上试用

在项目根目录使用 PowerShell：

```powershell
.\start-contractguard.bat --build --no-ai
```

打开启动器显示的地址。在两个规范编辑器下方的“调用方样例”区域，点击“载入调用方示例”，再点击“运行兼容性分析”。这个按钮同时填写基线规范、候选规范和三类调用方样例。

| 调用方 | 检查 | 预期结果 |
| --- | --- | --- |
| Mobile checkout | 数量为 1 的下单请求，新契约最小数量改为 2 | 请求样例回归 |
| Mobile checkout | 响应缺少调用方要求的 receiptUrl | 响应约束回归 |
| Revenue dashboard | 收入和币种仍满足原断言 | 样例通过 |
| European inventory sync | 原来的 eu 参数被新枚举移除 | 请求样例回归 |

合计为 **3 个调用方、3 个交互、4 项检查，3 项回归、1 项通过**。静态引擎另报告 2 项破坏性变更。两类数量不同是正常现象：一个规范变更可以影响多个调用方，调用方样例也可能暴露规范没有改变时的问题。

原始输入：[baseline.json](../fixtures/consumer-impact/baseline.json)、[candidate.json](../fixtures/consumer-impact/candidate.json)、[consumers.json](../fixtures/consumer-impact/consumers.json)。这些是合成零售案例，不是用户或企业生产数据。

## 准备自己的样例

使用 JSON，最多 1 MiB、50 个调用方、200 个交互；每个调用方至少一个交互，每个交互至少有 request 或 response。字段拼写错误会被拒绝，防止调用方配置被静默忽略。

```json
{
  "schemaVersion": 1,
  "consumers": [{
    "id": "mobile",
    "name": "移动端",
    "owner": "客户端团队",
    "criticality": "critical",
    "interactions": [{
      "id": "open-receipt",
      "method": "POST",
      "path": "/orders",
      "response": {
        "status": "201",
        "mediaType": "application/json",
        "baselineBody": {
          "id": "example-order",
          "status": "accepted",
          "receiptUrl": "/receipts/example-order"
        },
        "candidateBody": {
          "id": "example-order",
          "status": "accepted"
        },
        "expectation": {
          "type": "object",
          "required": ["id", "receiptUrl"],
          "properties": {
            "id": { "type": "string" },
            "receiptUrl": { "type": "string", "minLength": 1 }
          }
        }
      }
    }]
  }]
}
```

将这份 JSON 与上述零售基线、候选契约配合使用，可产生一个响应约束回归。保留更多调用方有助于判断影响范围，但没有提交样例的调用方不会被自动推断为安全。

字段约定：

- `id` 为稳定标识，只使用字母、数字、点、下划线、连字符；同一层级不能重复。生成的检查 ID 包含调用方 ID、交互 ID 和 request/response，重新运行同一清单可对应到同一交互。
- `method` 和 `path` 精确对应 OpenAPI 的操作，例如 `GET /orders/{id}`。这里是路径模板，不是完整 URL；不会猜测路由、发出 HTTP 请求或跟随重定向。
- `criticality` 为 `critical` 或 `standard`，用于迁移任务优先顺序。普通调用方的已证实样例回归同样会阻断调用方门禁。
- `request.parameters` 可以包含 `path/query/header/cookie` 四个对象，值是**解码后的 JSON 值**。字符串 `"1"` 不会自动转换为整数 `1`。参数继承和操作级覆盖按已实现的 OpenAPI 行为处理。
- `request.body` 出现时需要 `mediaType`。同一个旧请求样例分别检查旧、新契约，以判断新约束是否拒绝该旧请求。省略 body 与 JSON null 不同。
- `response` 需要固定的三位状态码、媒体类型、`baselineBody` 和调用方拥有的 `expectation`。缺少 `candidateBody` 允许保存为证据不足，不能当作通过。
- 响应检查同时验证旧样例满足旧提供方 Schema 和调用方断言、新样例满足新提供方 Schema 和**同一份**调用方断言。响应状态和媒体类型由输入声明；当前不会比较两次真实 HTTP 交互的头、状态转换或传输过程。
- `expectation` 是独立、有限支持的 JSON Schema 对象或布尔值，可使用其自身的本地引用。它不是一段脚本，不执行任意代码，也不从网络加载 Schema。

建议由调用方维护自己的断言与经脱敏的代表性交互。不要为消除失败而直接放宽断言；先确定客户端代码是否已经完成对应迁移。

## 怎样读结果

| 单项状态 | 含义 | 下一步 |
| --- | --- | --- |
| pass / 样例通过 | 旧、新检查均在支持范围内成立 | 仅保留对这些样例的结论，继续真实集成测试 |
| regression / 回归 | 基线成立，候选违反一个已知条件 | 查看失败路径，修复请求、响应处理或提供方兼容行为 |
| invalid-baseline / 基线无效 | 旧样例已不符合旧契约或原断言 | 修复基线证据，暂不能归因于本次升级 |
| inconclusive / 证据不足 | 缺少候选证据、存在未支持约束或达到工作上限 | 补充样例或执行其他验证，不算通过 |

每项结果都保留基线与候选校验状态、有限数量的失败代码和 JSON Pointer 路径。关联的 `CG-xxxx` 仅表示**同一操作上下文**，不声称每个规范 finding 都导致了这一失败；规范未变化的调用方回归可以没有任何关联 finding。

调用方门禁为 `blocked/review/pass`。有样例回归为 blocked；无回归但存在无效基线、证据不足、尚未映射到调用方的风险 finding，或静态覆盖范围不完整时为 review；其余才是样例范围内的 pass。迁移清单提供负责人、优先级、检查 ID、操作和重验条件，不会自动修改业务代码或向负责人发送通知。

原有 `score/compatible/summary/changes` 始终表达**静态契约结论**。即使静态分数为 100，调用方门禁仍可能 blocked。页面、历史列表和导出分别显示两类结论。

## 命令行与 CI

```powershell
pnpm.cmd contractguard compare fixtures/consumer-impact/baseline.json fixtures/consumer-impact/candidate.json --consumer-evidence fixtures/consumer-impact/consumers.json --format markdown
```

默认静态破坏和调用方回归均会导致退出 2。这是报告已生成、门禁被触发，不是程序崩溃。输入错误或运行错误退出 1，未触发选定门禁退出 0。

| 选项 | 规则 |
| --- | --- |
| `--fail-on breaking` | 默认静态门禁 |
| `--fail-on potentially-breaking` | 同时阻断静态潜在风险 |
| `--fail-on never` | 只关闭静态严重度门禁 |
| `--fail-on-incomplete` | 静态覆盖范围不完整时额外阻断 |
| `--fail-on-consumer regression` | 附加调用方样例时的默认规则；blocked 退出 2 |
| `--fail-on-consumer review` | blocked 或 review 均退出 2，适合证据必须完整的 CI |
| `--fail-on-consumer never` | 输出调用方结果，但关闭该门禁 |

显式设置调用方门禁时必须提供 `--consumer-evidence`，避免看似启用实际没有执行。单文件、多文件 `--bundle` 和规则策略仍可配合使用；不要用关闭静态门禁来暗示没采样到的调用方没有风险。

## 创建可携带的回归包

```powershell
pnpm.cmd contractguard compare fixtures/consumer-impact/baseline.json fixtures/consumer-impact/candidate.json --consumer-evidence fixtures/consumer-impact/consumers.json --write-regression-pack retail-regression.json --format json --output retail-report.json
pnpm.cmd contractguard verify-pack retail-regression.json --format markdown
```

包包含两个契约或显式多文件内容、规范化调用方清单、规则策略、精确引擎版本和 SHA-256 指纹。它可以移动到装有**相同引擎版本**的环境后离线重验，无需原文件目录、云端模型或真实接口地址。

- `--write-regression-pack` 只创建新文件，已有同名文件会拒绝覆盖。报告也不能覆盖自己的输入或回归包，包括可识别的路径别名。
- `verify-pack` 默认调用方门禁为更严格的 review；可以显式调整，与 compare 的默认 regression 区分。
- 指纹只检出内容变化，**不是签名、可信来源证明或加密**。修改输入后应重新分析并创建新包；升级引擎时也应明确重建。
- 常规历史和报告不保存样例正文；**回归包会保存原始样例和契约**。共享前自行脱敏，勿将凭据、个人数据和生产 payload 提交到公开仓库。
- 此包不是网络流量回放。verify-pack 重跑的是有限样例与约束检查，不会执行样例中的 URL。

## AI 如何参与

确定性验证不需要 DeepSeek 或其他模型。已有可选 AI 解释器在用户主动生成时，会收到有限的调用方状态、计数、问题代码和最多 16 项失败或待确认检查摘要；不发送样例正文、完整断言、负责人或全量契约。

新版提示词为 `ai-explainer-v4`，缓存绑定调用方结果。旧版已保存解释仍可读取。AI 不能改写分数和门禁，不能把调用方检查 ID 当成静态 finding ID；服务器会补充 blocked/review 的确定性提醒，即使模型给出低风险意见。自然语言结论本身仍不是完整事实证明。

## 明确支持边界

样例校验器支持类型、整数、枚举、适用方言的 const、对象属性与必填、additionalProperties、数组 items、整数 multipleOf、唯一元素、数值和长度/数量边界、三态组合逻辑，以及有界的本地/多文件引用和请求/响应方向性。OpenAPI 3.0 nullable 与 3.1 null 类型按方言处理。

pattern、format、非整数 multipleOf、prefixItems、patternProperties、未支持的关键字、自定义方言与作用域等会保留为未知；不会为了显示通过而跳过未知验证。认证、HTTP 参数序列化、multipart 编码、网络、响应头、时序、业务副作用与端到端流程不是这套检查的证明对象。文档结构没有经过完整 OpenAPI 元 Schema 校验，提供方契约本身仍应使用专门校验器检查。

每次值校验最多深度 64、10,000 步和 40 条问题；整组调用方验证另有 1,024 次 Schema 校验与 10,000 个参数声明扫描预算。命中上限返回无法确认。极端文件、未知方言和复杂组合的受支持范围应以测试和输出提示为准。

复现自动化：`pnpm.cmd regression:v14`；全量验证：`pnpm.cmd check`。详细结果见 [验证记录](verification.md)，官方工具对照见 [范围对照](v1.4-engine-comparison.md)。这些验证没有建立真实项目上的准确率优势。
