# V1.6：Codex 十个规范变更案例

这组测试验证一个实际使用过程：让 Codex 通过已安装的 ContractGuard 插件分析两个版本的 OpenAPI，读取变更明细，再到历史中确认结果已经保存。用例来自十种常见业务调整，覆盖六项明确破坏、一项潜在风险和三项兼容变更；兼容性判断使用 ContractGuard 原生规则的默认策略。

所有输入都是合成材料。每个案例只改变一个契约要素，便于追踪具体规则，避免多个变化相互掩盖。完整基线、候选、中文说明和预先定义的期望位于[测试数据](../fixtures/agent-plugin/codex-ten-cases.json)，执行及核验逻辑位于[验收脚本](../scripts/acceptance-codex-ten.mjs)。

## 十个案例分别在验证什么

| 编号与业务背景 | 具体规范差异 | 对旧调用方的影响 | 预期结果 | 处理建议 |
| --- | --- | --- | --- | --- |
| 01 · 电商旧订单查询下线 | 删除整个 `/legacy-orders` 路径，原有 `GET` 随之不可用 | 旧版移动端仍访问旧地址，无法继续获取订单 | `PATH_REMOVED`，明确破坏，`compatible=false` | 保留旧接口一段迁移期，记录旧客户端使用情况，完成迁移后再移除 |
| 02 · 发票服务引入多租户隔离 | 为 `GET /invoices` 新增必填请求头 `X-Tenant-Id` | 旧客户端没有传该请求头，原本有效的请求不再满足契约 | `PARAMETER_ADDED_REQUIRED`，明确破坏，`compatible=false` | 提供版本化入口或受控兼容方案，先升级调用方，再启用必填要求；不能省略租户校验来消除告警 |
| 03 · 支付服务停止接收钱包支付 | `POST /payments` 请求字段 `method.enum` 从 `[card, wallet]` 收窄为 `[card]` | 已接入钱包的调用方仍会提交 `wallet`，请求可能被拒绝 | `SCHEMA_ENUM_NARROWED`，明确破坏，`compatible=false` | 先确认钱包调用量、迁移支付入口；过渡期继续支持原值，或明确发布新版本 |
| 04 · 物流追踪编号改成数字 | `GET /shipment` 响应字段 `trackingId.type` 从 `string` 改为 `integer` | 旧 SDK 可能无法反序列化，编号的前导零也可能丢失 | `SCHEMA_TYPE_CHANGED`，明确破坏，`compatible=false` | 保留原字符串字段；如需数字字段，可新增独立字段并明确语义 |
| 05 · 后台任务增加“暂停”状态 | `GET /jobs` 响应字段 `state.enum` 在 `queued/running/done` 之外增加 `paused` | 旧客户端若穷举状态，可能无法展示或处理 `paused`；有兜底分支的客户端未必受影响 | `SCHEMA_ENUM_WIDENED`，潜在破坏，`compatible=true` | 检查客户端状态分支和 SDK 枚举容错；补充真实调用方样例后决定是否发布 |
| 06 · 用户资料不再保证返回邮箱 | `GET /profile` 保留 `email` 的字段定义，但把它从响应 `required` 中移除 | 字段仍在文档中，但现在允许缺失；依赖必有邮箱的旧代码可能报错 | `SCHEMA_REQUIRED_PROPERTY_REMOVED`，明确破坏，`compatible=false` | 先让调用方处理缺失值，或在旧版本继续保证字段存在；不要仅因为“字段没有删除”就忽略变化 |
| 07 · 异步导出响应约定调整 | `POST /exports` 原有 `200` 和 `202`，候选删除 `202`，保留 `200` | 旧客户端可能依赖 `202` 进入后台任务轮询；成功响应约定发生变化 | `RESPONSE_STATUS_REMOVED`，明确破坏，`compatible=false` | 在旧版本保留异步流程，或说明新的任务接收及轮询协议并同步升级调用方 |
| 08 · 商品搜索增加分类筛选 | `GET /products` 新增可选查询参数 `category` | 旧客户端可以继续不传，原有请求仍然有效 | `PARAMETER_ADDED_OPTIONAL`，兼容，`compatible=true` | 保持省略参数时的旧行为，为新增筛选功能补充示例 |
| 09 · 监控平台增加指标入口 | 保留 `GET /health`，新增独立的 `GET /metrics` | 原有客户端调用不受影响，新客户端可选择使用新增入口 | `PATH_ADDED`，兼容，`compatible=true` | 按新增功能正常发布；另行检查访问控制、限流和指标内容，契约兼容测试不会替代这些检查 |
| 10 · 备注服务允许更长文本 | `POST /notes` 请求字段 `text.maxLength` 从 `100` 放宽到 `500` | 原本允许的所有文本仍然合法，新客户端可以提交更长文本 | `SCHEMA_CONSTRAINT_RELAXED`，兼容，`compatible=true` | 确认存储、下游和展示确实能接收 500 字符，避免规范放宽而实现没有同步 |

03、05、06、10 使用 OpenAPI 3.1.0，其余使用 3.0.4。每例预期一个 finding；默认策略下，明确破坏案例为 88 分，潜在风险案例为 96 分，其余为 100 分。分数用于表达当前规则计算出的风险，不是发布成功率。

## 为什么第五例仍然显示 compatible=true

`compatible` 在现有原生分析中表示“没有级别为 breaking 的 finding”。第五例的输出状态枚举扩大被标记为 `potentially-breaking`：有些旧客户端能处理未知状态，有些不能，仅凭这份契约无法确定全部调用方的行为。因此 `compatible=true` 与潜在风险告警同时出现是本例的预期结果，不能解释为“可以放心发布”。

第三例和第五例也展示了请求、响应方向的差别。请求枚举收窄会直接排除原来合法的输入；响应枚举扩大则会向旧客户端提供它们未预期的新值。不能仅按“新增通常安全、删除通常危险”来判断兼容性。

## 测试怎样确认工具真的执行了

每个案例启动一个真实 Codex 会话，依次调用 `contractguard_status`、`contractguard_analyze`、`contractguard_get_analysis`、`contractguard_list_analyses`。分析只提交一次；创建结果不确定时不自动重复提交，以免生成重复历史。

验收脚本核对 Codex 的实际 MCP 工具事件及成功状态，深比较模型提交的输入与原始 fixture，检查返回的分析 ID、规则和严重程度，再将 MCP 明细与 HTTP 已保存记录对照。宿主查询到的历史必须包含刚创建的同一个 ID；模型最后一句“测试通过”不作为通过证据。

这里参与编排的是 Codex 自身的模型，分析判断由确定性工具完成。脚本不调用 `contractguard_explain_analysis` 或 `contractguard_start_review`，因此这组案例不会另外触发 ContractGuard 内部的 DeepSeek 解读或自主审查请求。真实 Codex 调用仍会消耗用户自己的 Codex 使用额度。

## 在本机复现

先启动 ContractGuard 本机服务，确认 `http://127.0.0.1:8080` 可访问，并按照[插件使用说明](v1.6-agent-plugin.md)安装、启用 Codex 插件。脚本使用已有 Codex 登录，不要求复制账号凭据或再次提供 DeepSeek Key。

在项目根目录运行以下命令。`--run` 是显式执行开关：执行会调用真实 Codex 模型，并在当前本机服务中创建分析历史；不会删除已有记录。输出目录应使用新的目录名，避免覆盖之前的验收材料。

```powershell
node scripts/acceptance-codex-ten.mjs --run --output ../ContractGuard-codex-ten-results
```

也可只执行一个指定案例：

```powershell
node scripts/acceptance-codex-ten.mjs --run --case CG-CODEX-05 --output ../ContractGuard-codex-case05-results
```

不加 `--run` 只显示用法，不调用模型。真实模型验收没有加入默认 `pnpm check` 或 CI，以免普通测试意外消耗额度、写入用户历史。

运行过程保留 Codex 的 `code_mode_host`，通过临时参数 `features.code_mode.direct_only_tool_namespaces=["mcp__contractguard","contractguard"]` 让 ContractGuard 使用直接工具调用，避开此前 alpha 版的嵌套 JavaScript 分派问题。该参数来自 [Codex 官方配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)。同时临时关闭 shell 工具和 Apps 接入，并限制为只读环境；不改动全局 Codex 配置，也不替换已安装插件。

## 覆盖边界

这十个案例验证的是代表性的单点 OpenAPI 变更，以及 Codex → MCP → 本机服务 → 历史保存的完整链路。它们不覆盖全部 OpenAPI 语义，也不证明其他宿主、操作系统或模型版本同样稳定。

本组没有提供调用方回放证据，没有访问真实业务接口，也没有测试鉴权实现、数据迁移、性能、复杂组合 Schema、多文件引用或 DeepSeek 自主审查。所有预期都针对默认原生规则；自定义策略或 oasdiff 的判断可能不同。真实发布仍需结合具体调用方、实现行为与已有专项验证。
