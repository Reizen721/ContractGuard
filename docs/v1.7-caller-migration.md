# V1.7：调用方源码定位与迁移验证

本文说明独立调用方模块的有限重放边界。V1.8 已把它接入内置 Agent，并新增独立标识的真实项目测试执行器；当前安装与使用见 [V1.8 指南](v1.8-project-agent.md)。下文“不执行 Node.js”仅指此 AST 重放模块。

本版把 API 变更审查推进到调用方源码：提交新旧契约、TypeScript 文件和明确的响应场景后，可以定位调用行，比较原函数在两组样例下的表现，并验证显式字段重命名产生的候选补丁。

**验证方式是有限的 TypeScript AST 解释重放，标识为 `bounded-typescript-replay`。** 系统解析并解释提交源码中受支持的函数逻辑；不会把这些文件交给 Node.js 执行，不运行项目完整测试，也不请求真实业务 API。报告中的通过或回归只适用于所提供的场景与支持范围。

新模块与 MCP 插件版本为 `1.7.0`；原生契约引擎仍为 `1.5.0`。已有普通分析、oasdiff 完整审查、AI 解读、历史和导出继续保留。新的调用方审查使用单独的历史记录。

## 1. 一个具体场景

订单接口的响应字段从 `customerName` 迁移到 `displayName`。调用方仍然执行：

```typescript
export async function orderLabel() {
  const response = await fetch('/orders/current');
  const order = await response.json();
  return order.customerName.toUpperCase();
}
```

给出基线响应 `{ "id": "ORD-101", "customerName": "Alice" }`、候选响应 `{ "id": "ORD-101", "displayName": "Alice" }`，以及明确预期 `"ALICE"`，系统会检查响应是否符合对应契约，再重放该函数。基线可以得到预期字符串；候选数据无法满足旧字段访问逻辑。

只有当操作者确认了 `customerName → displayName` 的语义映射，并通过 `fieldRenames` 提交时，系统才尝试修改可归因于该响应的属性访问。修改发生在内存副本，随后重新检查该文件的全部已提交场景。它不会因为删除一个字段、新增另一个字段，就自行认定两者含义相同。

即使补丁达到 `verified`，报告仍保留原始回归和静态契约门禁。这里表达的是“这个候选修改通过了列出的有限场景”，不是“旧客户端已经修好”或“可以直接发布”。

## 2. 直接可用的输入

完整、自包含且不含凭据的 JSON 输入位于 [fixtures/caller-impact/input.json](../fixtures/caller-impact/input.json)。它可以直接导入网页、提交给 HTTP API，或作为 MCP 工具参数，不需要另外读取源码路径。

CLI 可使用同一材料的分拆文件：

| 文件 | 用途 |
| --- | --- |
| [baseline.json](../fixtures/caller-impact/baseline.json) | 原始 OpenAPI 契约 |
| [candidate.json](../fixtures/caller-impact/candidate.json) | 字段变更后的契约 |
| [src/orders.ts](../fixtures/caller-impact/src/orders.ts) | `fetch` 订单显示及订单编号调用 |
| [src/profile.ts](../fixtures/caller-impact/src/profile.ts) | `axios.get` 联系邮箱调用 |
| [scenarios.json](../fixtures/caller-impact/scenarios.json) | 三个响应场景、参数及明确输出预期 |
| [field-renames.json](../fixtures/caller-impact/field-renames.json) | 两项显式字段映射 |
| [cases.json](../fixtures/caller-impact/cases.json) | 对照、失败与不支持场景的回归集 |

主演示的三个场景分别检查订单显示名称、保持不变的订单编号、联系邮箱。当前实现下应得到 **两项回归、一项通过、两份已在副本中验证的补丁，原始门禁保持 `blocked`**。

输入的顶层字段固定如下，不接受 API Key、任意命令、服务器磁盘路径或网络目的地：

| 字段 | 含义 |
| --- | --- |
| `schemaVersion` | 固定为 `1` |
| `baseline`、`candidate` | 契约文本、对象或已有格式的显式多文件包 |
| `files` | `{path, content}` 数组；路径只作为相对来源标识，内容必须显式提交 |
| `scenarios` | 场景数组；可以为空，但无场景不构成验证通过 |
| `fieldRenames` | 可选的 `{method, path, from, to}` 数组；操作者确认的顶层响应字段映射 |

一个场景示例：

```json
{
  "id": "order-label",
  "file": "orders.ts",
  "exportName": "orderLabel",
  "args": [],
  "operation": { "method": "GET", "path": "/orders/current" },
  "baselineResponse": {
    "status": 200,
    "body": { "id": "ORD-101", "customerName": "Alice" }
  },
  "candidateResponse": {
    "status": 200,
    "body": { "id": "ORD-101", "displayName": "Alice" }
  },
  "expected": "ALICE"
}
```

`file` 必须精确匹配 `files[].path`，CLI 中则匹配相对于 `--source-root` 的路径。`operation.method` 使用大写；`operation.path` 是 OpenAPI 路径模板。`args` 与导出函数参数一一对应。`expected` 是必填的 JSON 值；不能仅因两个响应内容不同就认定调用方回归。

## 3. 更新本机安装

在包含 V1.7 源码的项目目录执行：

```powershell
pnpm install --frozen-lockfile
pnpm build
pnpm plugin:prepare
```

随后停止并重新启动原来的 ContractGuard API 服务，例如重新运行 `start-contractguard.bat`。只更新 MCP 文件、保留旧服务运行，会导致新 `/api/caller-reviews` 路由不可用。这个功能本身无需 DeepSeek Key，也不触发内部云模型调用。

将宿主使用的插件更新为新生成的 `.tools/agent-plugin/plugins/contractguard/`，或更新对应的直接 MCP 配置。使用完整插件的宿主可能缓存插件副本，需要按其本地插件更新/重新导入流程替换旧版本。**服务端与宿主 MCP 进程都要加载新代码**；重启宿主或刷新连接后开启新会话，工具列表应出现下面四个新工具，总数为 **18**。普通 MCP 配置与完整插件仍选择一种安装方式，避免重复工具。

通用安装和 Codex、Antigravity、DeepSeek Harness 的配置结构继续参照 [V1.6 接入指南](v1.6-agent-plugin.md)。该指南中的 14 个工具是上一版集合；本版在其基础上新增调用方审查工具。

## 4. 网页操作

打开本机网页，进入导航中的 **“调用方迁移”**；窄屏导航名称为“调用方”。

1. 点击“载入迁移示例”，或导入完整的 `input.json`。
2. 检查输入中的契约、源码、场景及字段映射，提交审查。
3. 查看调用位置、基线/候选结果、未解析调用和候选补丁。
4. 查看每份补丁的验证状态；通过只针对报告列出的场景。
5. 在该页面的独立历史中重新打开记录，或下载 JSON/Markdown 报告。

网页导入的是显式 JSON 包，不会遍历磁盘上的调用方仓库。项目目录的受控收集入口在 CLI；Agent 也可以使用宿主自身已获授权的文件读取能力，准备同样的输入包。

## 5. CLI 收集源码并导出候选补丁

从项目根目录运行以下 PowerShell 示例。输出文件和目录必须尚不存在；重复执行时换一个输出名称。

```powershell
pnpm contractguard review-callers `
  fixtures/caller-impact/baseline.json `
  fixtures/caller-impact/candidate.json `
  --source-root fixtures/caller-impact/src `
  --scenarios fixtures/caller-impact/scenarios.json `
  --renames fixtures/caller-impact/field-renames.json `
  --format markdown `
  --output outputs/caller-review-v17.md `
  --write-patches outputs/caller-patches-v17
```

示例原始门禁为 `blocked`，默认退出码 **2** 是预期的审查结果；报告和候选补丁仍会写出。退出码 **1** 表示输入、文件操作或执行失败；退出码 **0** 表示没有触发选定的失败阈值。`--fail-on never` 可以仅生成材料，但不会把报告中的 `blocked` 改成 `pass`。

| 选项 | 行为 |
| --- | --- |
| `--source-root` | 必填；只读取这个明确目录下的 `.ts` / `.tsx` 文件 |
| `--scenarios` | 必填；包含场景数组的 JSON 文件；`[]` 只做有限定位 |
| `--renames` | 可选；显式映射数组，没有映射时不猜测改名 |
| `--format` | `json` 或 `markdown`，默认 Markdown |
| `--output` | 在源码根目录外创建新的报告文件，不覆盖已有文件 |
| `--write-patches` | 在源码根目录外创建全新目录，导出候选源码、diff 和验证清单；不应用补丁 |
| `--fail-on` | 默认 `review`：`blocked` 或 `review` 返回 2；`regression` 仅在总门禁 `blocked` 时返回 2；`never` 不因门禁返回 2 |
| `--bundle` | 按已有受控规则加载契约本地依赖；可配合 `--baseline-root`、`--candidate-root` |

源码收集跳过隐藏项、声明文件，以及 `node_modules`、`dist`、`build`、`coverage`、`vendor` 目录；不跟随符号链接。超出 20 个文件、1 MiB 总内容、每文件 256 KiB、2,000 个目录项或 30 层目录深度时停止并报错，不静默截断。

补丁输出目录包含 `manifest.json`、`patches.json`、`patches/*.diff` 和 `sources/` 下的候选源码。清单记录原始/候选 SHA-256、验证状态和结果。应用前应由维护者核对当前源码指纹、审阅差异，并运行项目自己的测试。本版没有自动应用补丁或推送 PR 的命令。离线 CLI 输出不会自动加入网页/API 历史。

## 6. HTTP API

| 方法与路径 | 行为 |
| --- | --- |
| `POST /api/caller-reviews` | 提交完整输入；成功返回 `201` 和 `{id, createdAt, report}` |
| `GET /api/caller-reviews` | 返回 `{reviews: [...]}`；按创建时间倒序的摘要历史 |
| `GET /api/caller-reviews/:id` | 返回保存的完整记录 |
| `GET /api/caller-reviews/:id/report?format=json` | 导出完整记录；`format=markdown` 返回可读报告 |

PowerShell 提交完整示例：

```powershell
$callerInput = Get-Content -LiteralPath 'fixtures/caller-impact/input.json' -Raw -Encoding UTF8
$callerReview = Invoke-RestMethod `
  -Method Post `
  -Uri 'http://127.0.0.1:8080/api/caller-reviews' `
  -ContentType 'application/json; charset=utf-8' `
  -Body ([System.Text.Encoding]::UTF8.GetBytes($callerInput))

$callerReview.id
$callerReview.report.summary
$callerReview.report.gate
```

服务端以独立 worker 执行固定的 AST 分析程序，最多两个并行任务、每次 15 秒时间限制，并设置 worker 内存上限。它不会把用户源码当作 worker 脚本执行。HTTP 请求取消会终止仍在运行的解释任务；如果连接在保存阶段中断，客户端应先查历史，不要盲目重复创建。

新历史保存在配置的数据目录下的 `caller-reviews/`。只保存结果，不保存完整原始输入包；结果可能包含源文件路径、候选源码、补丁及观测值。JSON 导出是带记录 ID 和时间的完整 envelope；CLI JSON 则是 `report` 本身。

## 7. MCP 工具

原有 14 个工具保持不变，新增：

| 工具 | 用途 |
| --- | --- |
| `contractguard_review_callers` | 提交与 HTTP 相同的完整输入，创建记录并返回摘要 |
| `contractguard_get_caller_review` | 按 `callerReviewId` 读取 `overview`、`callsites`、`checks`、`patches` 或 `limitations` |
| `contractguard_list_caller_reviews` | 查询调用方审查独立历史 |
| `contractguard_export_caller_review` | 导出 JSON/Markdown，按返回的 `nextOffset` 读取并拼接所有分块 |

详情和历史沿用 `offset`、`limit`，每页默认 20、最多 50 项。导出沿用 UTF-16 偏移，默认每块 24,000、最多 32,000 字符；不能只保存第一块就称完整报告。过大的单项补丁可通过分块导出读取。

可以在已更新的 Agent 中输入：

> 使用 ContractGuard 检查状态，读取本仓库 `fixtures/caller-impact/input.json`，按原始内容调用 `contractguard_review_callers`。查询返回记录的调用位置、检查、补丁和限制，说明哪些场景发生回归、哪些补丁已在副本中验证，以及原始门禁为何仍是 blocked。通过调用方历史确认记录已保存，并完整导出 Markdown。不要修改源码或把有限解释重放称为完整项目测试。

## 8. 如何解释结果

| 状态 | 含义 |
| --- | --- |
| `pass`（检查） | 两侧样例通过相应约束，受支持的函数重放均满足显式输出预期 |
| `regression` | 基线通过，候选重放发生受支持的运行错误或不满足同一预期 |
| `invalid-baseline` | 基线已经不满足要求，不能把它当成新引入的回归 |
| `inconclusive` | 语法、契约范围、操作匹配或样例有效性不足，不能形成完整结论 |
| `unknown`（调用点） | 无法可靠解析调用目标或方法，需进一步调查 |
| `verified`（补丁） | 复现了原始回归，基线有效，已知调用点有场景覆盖，同文件全部已提交场景在修改副本后通过 |
| `failed` / `unverified`（补丁） | 存在失败场景，或尚不满足完整的本版验证条件；不能作为已验证修复 |

总门禁 `gate` 同时考虑原始静态契约风险与调用方证据。明确破坏或回归会阻断；未覆盖范围、未知调用、无效基线、缺失场景等会要求复核。报告里的 `relatedChangeIds` 提供同操作的静态上下文，不表示每个关联变更都是该次失败的确切原因。

## 9. 当前支持范围与证据边界

本版面向具名导出的异步函数，识别字面量 URL 的 `fetch` 和默认导入 Axios 的常见方法调用；可解释有限的 `const` 绑定、属性访问、基础表达式、`if` / `switch`、若干字符串方法及 JSON 响应。每个场景必须恰好执行一次可归因请求。Axios 导入只用于识别调用形式，不加载或执行 Axios 包。

动态 URL、包装后的客户端、任意依赖、模块初始化、可变状态、不支持的语法等不能按完整 JavaScript 语义执行；具体限制会出现在结果中。`.tsx` 可以提交，但这不表示支持 JSX 渲染、React 生命周期或组件集成测试。响应字段使用位置来自实际重放到的样例路径，未执行的分支不在这份证据内。

请求体、请求头、认证、序列化、网络故障、重试、数据库与业务副作用没有在这个重放器里验证。输入最多 30 个场景、每场景 16 个参数及 128 KiB，最多 20 个改名映射；解释步骤、表达式深度与 AST 节点也有上限。超出范围不能转成成功。

字段补丁仅支持操作者明确确认的顶层响应属性映射，且要求相关新旧响应 schema 能证明相应属性存在。代码中没有被可靠归因或没有经过样例路径的读取，不会被当作全局字符串替换目标。有限样例验证不是对补丁语义、所有分支或生产安全的保证。

报告可能含源码副本、路径、diff 和观测样例值；分享或上传之前需要按项目数据要求检查。API/MCP 本身不调用模型，但外部云端 Agent 可能将其读取的材料及工具结果送入自身模型服务。输入指纹用于一致性检查，不是数字签名或不可篡改审计证明。

## 10. 验证与后续工作

回归材料涵盖正常对照、真实源码重放回归、未知调用、无效基线、候选补丁验证和保守拒绝行为；HTTP/MCP 验证还检查持久化、重启恢复、分页和导出。精确的已执行命令、结果与尚未验证范围统一记录在[验证记录](verification.md)，不将合成案例通过率当作真实项目准确率。

下一步可在明确授权和执行隔离下接入项目真实测试，扩大代码形态与真实调用方语料，并用公开对照集评估定位、误报、漏报和修复效果。本版没有自动安装调用方依赖、执行任意测试命令、采集生产流量或创建迁移 PR。
