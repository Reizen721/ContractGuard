# V1.3：20 个固定场景顺序验收

这组案例用可检查的 baseline/candidate 文件验证多文件解析、规则方向、方言边界和明确拒绝行为。它们是人工预先标注期望的合成场景，不是从真实 API 数据集测得的准确率，也不是 20 次浏览器测试。本页说明案例与断言机制；某次运行是否通过，应以该次输出和[验证记录](./verification.md)为准。

输入位于 `fixtures/v1.3-acceptance/case-01` 至 `case-20`，期望分别保存在[案例 01—10 清单](../fixtures/v1.3-acceptance/cases-01-10.json)与[案例 11—20 清单](../fixtures/v1.3-acceptance/cases-11-20.json)。每项明确列出入口、提供的文件、完整 finding 等级集合或应返回的错误。预期先于运行结果编写，不能为迎合当前输出而修改标签。

## 运行与保存证据

在项目根目录运行；首次使用或源码变更后先构建：

```bash
pnpm build
pnpm acceptance:v13
```

`pnpm check` 也包含此套件。需要保留逐例证据时，在已构建的项目根目录运行：

```bash
node scripts/acceptance-v13.mjs --output-dir ../ContractGuard-v1.3-20-case-results
```

Windows PowerShell 如果不能直接运行 `pnpm`，将其替换为 `pnpm.cmd`。输出目录会保留本次 `README.md` 概览、`results.json` 汇总和 `case-01.json` 至 `case-20.json` 的期望与实际 Core/API/CLI 证据；有效分析另有对应 `.md`、`.html` 报告。重复使用同一输出目录会覆盖同名证据文件，可换一个目录保留不同轮次。

脚本使用独立临时历史目录和仅监听回环地址的 HTTP 服务，执行后关闭服务并清理临时数据；显式输出目录中的证据保留。AI 在测试服务中关闭，没有真实 LLM 调用，不需要模型 key，也不使用用户已有历史目录。

## 固定场景与预期

下表中的 `complete` 只表示当前规则未发现已知覆盖缺口，不是形式化兼容性证明。`partial` 表示仍有待复核内容；拒绝输入不生成分析报告，因此没有 coverage 值。

| 编号 | 场景 | 预期 finding 等级或错误 | coverage |
| --- | --- | --- | --- |
| case-01 | 等价 JSON/YAML，重排对象键与属性顺序 | 无 finding | complete |
| case-02 | 删除整条 `/legacy` 路径，并删除保留路径上的 DELETE 操作 | `PATH_REMOVED`、`OPERATION_REMOVED`，均 breaking | complete |
| case-03 | 新增必填 query 参数 `tenantId` | `PARAMETER_ADDED_REQUIRED`，breaking | complete |
| case-04 | 新增可选 query 参数 `pageToken` | `PARAMETER_ADDED_OPTIONAL`，non-breaking | complete |
| case-05 | 删除响应中原本必需的 `id` 属性 | `SCHEMA_PROPERTY_REMOVED`，breaking | complete |
| case-06 | 请求枚举不再接受 `cancelled` | `SCHEMA_ENUM_NARROWED`，breaking | complete |
| case-07 | 响应枚举新增 `cancelled` | `SCHEMA_ENUM_WIDENED`，potentially-breaking | complete |
| case-08 | 请求 `quantity` 的 minimum 从 1 提高为 2 | `SCHEMA_CONSTRAINT_TIGHTENED`，breaking | complete |
| case-09 | 响应引用外部模型，`id` 从 string 改为 integer | `SCHEMA_TYPE_CHANGED`，breaking；定位模型文件 | complete |
| case-10 | 三文件传递引用，嵌套 `postalCode` 从 string 改为 integer | `SCHEMA_TYPE_CHANGED`，breaking；定位第三个文件 | complete |
| case-11 | 跨文件 3.0 nullable 迁移到 3.1 null 联合类型，值集合等价 | 无 finding | complete |
| case-12 | 3.1 Schema 增加旧式 `nullable: true` | 无 finding；`OAS31_NULLABLE_IGNORED` 告警 | partial |
| case-13 | 未知 `$schema` 方言下变更字段类型 | `SCHEMA_UNSUPPORTED_KEYWORD_CHANGED`，potentially-breaking；`UNSUPPORTED_SCHEMA_DIALECT` 告警 | partial |
| case-14 | 两侧相同 webhook 与本地依赖 | 无 finding；`WEBHOOKS_NOT_ANALYSED` 告警 | partial |
| case-15 | Path Item 引用 GET，同时删除本体的非冲突 POST | `OPERATION_REMOVED`，breaking | complete |
| case-16 | Path Item 引用目标与本体的 GET 冲突 | 无精确差异 finding；`PATH_ITEM_REFERENCE_CONFLICT` 告警 | partial |
| case-17 | 候选引用未提供的 `schemas/missing.json` | `INVALID_BUNDLE`；标明缺失文件 | —，拒绝输入 |
| case-18 | 候选引用 HTTPS 远程 Schema | `INVALID_BUNDLE`；拒绝远程获取 | —，拒绝输入 |
| case-19 | 候选使用 `../outside.json` 逃逸包根 | `INVALID_BUNDLE`；拒绝越界 | —，拒绝输入 |
| case-20 | 候选使用 `#Value` 命名 anchor | `INVALID_REFERENCE`；明确尚不支持 | —，拒绝输入 |

这里有 16 个应生成正常分析的输入对，以及 4 个应拒绝的输入对。“正常分析”包括检出 breaking 的报告，不代表契约兼容；4 个拒绝案例如果按期望拒绝，同样算验收通过。只有实际行为与标签不符才算案例失败。

## 脚本断言了什么

摘要的五项计数和默认 CLI 退出码直接从预先标注的 findings 计算；incomplete 门禁的预期直接来自清单的 coverage。不能仅让三个入口彼此一致，否则共享的计数错误可能被误当成通过。

[顺序验收脚本](../scripts/acceptance-v13.mjs)按编号逐例调用 Core、HTTP API 与 CLI，使用同一份显式文件内容和固定测试策略。有效输入检查 `compatible`、coverage、完整的 `ruleId + severity` 多重集合、指定告警及跨文件来源；随后比较三入口的证据、摘要、指纹和结论，排除 ID、时间等边界字段，并按 JSON 语义处理不存在的可选字段。

有效案例还检查历史保存与读取、Markdown/HTML 导出的 coverage 状态及策略信息。全部案例执行后，脚本关闭并重启 HTTP 服务，读取同一临时目录，核对成功历史及其 finding、coverage、来源恢复。错误案例要求 Core/API 返回清单指定错误、API 返回 400、CLI 退出 1 且不输出成功 JSON 报告，同时历史数量不增长。

脚本另对每份有效输入验证默认 CLI 门禁和独立的 incomplete 门禁。只要某例断言不符或重启恢复不符，套件最终退出非零；终端会逐例显示 PASS/FAIL，输出目录记录实际证据。它不验证浏览器目录选择器、页面像素布局、云端模型质量、生产环境性能或全部 OpenAPI 语义。

## 手动复核 CLI 与来源

以下命令在项目根目录的 PowerShell 中执行。case-09 默认会生成报告并以 2 退出，因为检出了 breaking；这表示门禁生效，报告本身仍然有效：

```powershell
pnpm.cmd contractguard compare fixtures/v1.3-acceptance/case-09/baseline/openapi.json fixtures/v1.3-acceptance/case-09/candidate/openapi.json --bundle --format json --output ../ContractGuard-v1.3-20-case-results/case-09-cli.json
$LASTEXITCODE
$report = Get-Content ../ContractGuard-v1.3-20-case-results/case-09-cli.json -Raw -Encoding UTF8 | ConvertFrom-Json
$report.changes | Select-Object ruleId, severity, sourceLocations | ConvertTo-Json -Depth 6
```

应看到 `SCHEMA_TYPE_CHANGED`，且 `sourceLocations.old/new` 均指向 `schemas/order.json` 的 `#/properties/id/type`。case-10 的对应来源为 `schemas/address.json#/properties/postalCode/type`。替换命令中的案例目录即可复核其他有效输入；case-01 的候选入口是 `openapi.yaml`，请按清单使用实际文件名。

case-17 故意没有提供被引用的模型文件，手动运行应明确失败：

```powershell
pnpm.cmd contractguard compare fixtures/v1.3-acceptance/case-17/baseline/openapi.json fixtures/v1.3-acceptance/case-17/candidate/openapi.json --bundle --format json
$LASTEXITCODE
```

预期退出码为 1，错误指出缺失 `schemas/missing.json`，不输出成功分析报告。CLI 的文本错误不等于 HTTP 的 JSON 错误结构；清单中的 `INVALID_BUNDLE` 由 Core 和 API 的结构化错误断言确认。

## 门禁结果如何理解

| 调用方式或结果 | 预期退出行为 |
| --- | --- |
| 默认 `--fail-on breaking` | 有 breaking 时退出 2，否则退出 0；partial 本身不触发默认门禁 |
| `--fail-on potentially-breaking` | 有 breaking 或 potentially-breaking 时退出 2 |
| `--fail-on never` | 有效分析不按 finding 等级退出 2 |
| `--fail-on never --fail-on-incomplete` | 有效分析 coverage 为 partial 时仍退出 2；complete 时退出 0 |
| 非法输入、缺文件或不支持的引用 | 退出 1；`--fail-on never` 不会把输入错误变成成功 |

例如 case-14 两侧 webhook 相同，没有 breaking，默认退出 0；显式增加 incomplete 门禁后应退出 2：

```powershell
pnpm.cmd contractguard compare fixtures/v1.3-acceptance/case-14/baseline/openapi.json fixtures/v1.3-acceptance/case-14/candidate/openapi.json --bundle --format json --fail-on never --fail-on-incomplete
$LASTEXITCODE
```

case-07 与 case-13 仅有 potentially-breaking，`compatible` 按现有定义仍为 true，默认门禁也不拦截；团队可选择更严格的等级门禁。`compatible`、finding 等级与 coverage 应一起阅读，不能用其中一个字段替代其余证据。更多边界见 [V1.3 指南](./v1.3-upgrade.md)。
