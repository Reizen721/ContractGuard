## 如何判定通过

本次宿主逐例实际调用 `contractguard_status`、`contractguard_analyze`、`contractguard_get_analysis` 和 `contractguard_list_analyses`。详情查询使用创建工具返回的分析 ID，三轮结果表中的 ID 均与已保存记录一致。验收保留各批工具卡、返回内容和模型选择界面，不以模型最终回复“完成”作为唯一依据。

随后运行了[独立只读核验脚本](../scripts/verify-antigravity-ten.mjs)，只通过 GET 读取已经保存的记录。十例的输入对象指纹、预期规则与严重程度、兼容性、计数、coverage 和历史/详情一致性均通过核验，每例恰有一条记录。脚本本身不调用模型、不创建分析，也不修改宿主配置。

两类证据互相补充：UI 证明所选宿主模型确实调用工具；GET 核验确认数据已经正确保存。仅凭 HTTP 记录无法证明创建者是 Antigravity 或某个 Gemini 型号，因此脚本中的 `hostToolTrace.verified` 保持 `false`，需要另附 UI 证据。

本次 UI 文本读取有 **20,000 字符上限**，仅部分展开返回取得了可完整解析的 JSON。已观察全部 40 张调用卡，但没有逐字段核验全部 40 份 UI 返回；完整结果检查针对的是所有十条持久化记录及其源指纹。两者不能混写成“40 次返回均已完整解析核验”。

本次执行的只读核验命令为：

```powershell
node scripts/verify-antigravity-ten.mjs --prefix ag-gemini38-20261102-01 --output ../ContractGuard-antigravity-gemini38-ten-20261102-verify01
```

该目录现已保存本次材料。复现时必须另选尚不存在的新输出目录，父目录应已存在，避免覆盖前次证据。原始 GET 报告保留其 `hostToolTrace.verified=false` 边界；合并 UI 证据的宿主验收汇总另存于证据目录，不改写原始报告。

## 范围与限制

本轮只测试原生分析与历史链路，不调用 `contractguard_explain_analysis` 或 `contractguard_start_review`，因此不额外触发 ContractGuard 内部的 DeepSeek 解读或自主审查。Gemini 宿主自身仍可能消耗用户的模型额度。

这些案例覆盖代表性的单点契约变更，不覆盖全部 OpenAPI 语义、调用方回放、鉴权实现、多文件引用或上游 oasdiff 全套检查；也不能由某次验收推断其他宿主或模型版本始终稳定。相关接入说明见[插件使用文档](v1.6-agent-plugin.md)，汇总验证见[验证记录](verification.md)。
