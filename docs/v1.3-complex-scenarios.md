# V1.3：8 个复合业务场景

这组输入把多处变更放进同一次业务发布：请求校验、鉴权、共享模型、响应保证和媒体类型可能同时变化，多个操作也可能引用同一个模型。目标是检查 ContractGuard 在组合条件下是否漏掉应报告的变化、误报未变内容，或把未覆盖范围误当作安全。

每组包含 baseline/candidate 真实 YAML/JSON 文件、外部引用、多个操作和未变控制端点。它们是固定标签的合成契约，不是八套已部署的业务系统。脚本调用的是 ContractGuard 的分析 API；下面的旧客户端交互用于说明独立预期，不代表脚本实际部署并调用了电商、身份或设备服务。此页记录预期与断言机制，某轮实际结果见[验证记录](./verification.md)及该轮输出证据。

## 运行与证据

在项目根目录执行；首次使用或源码变更后先构建：

```bash
pnpm build
pnpm scenarios:v13
```

保留完整证据：

```bash
node scripts/scenarios-v13.mjs --output-dir ../ContractGuard-v1.3-complex-results
```

Windows PowerShell 可使用 `pnpm.cmd`。输出目录包含 `README.md`、`results.json`、各场景 ID 对应的 JSON 证据及有效分析的 Markdown/HTML 报告。JSON 保留预期、实际 Core 结果、API 响应和 CLI 标准输出/错误；重复使用同一目录会覆盖同名文件。

套件使用固定测试策略 `v13-scenarios`、独立临时历史目录和仅监听回环地址的分析服务。执行后关闭服务、清理临时历史，显式输出目录继续保留。AI 关闭，不需要模型 key，没有真实 LLM 调用，不使用用户已有历史。

## 业务反例与未变控制

### 电商结算：旧请求与新响应都要检查

旧客户端可以使用 EUR 结算、提交 50 个最小货币单位，或省略可选的 `Idempotency-Key`。候选分别移除 EUR、将最低金额提高到 100、要求幂等 header，这三项各有独立的旧合法请求会被拒绝。把所有要求合在一个无效请求里，只能发现一次失败，无法证明三项都被识别。

创建响应和 `GET /orders/{orderId}` 复用 `schemas/order.json`。旧客户端按字符串处理 `id`，新整数类型会破坏该假设；新 `refunded` 状态可能超出旧穷举分支，所以两个操作都应报告类型 breaking 和枚举 potentially-breaking。来源检查定位幂等参数文件、结算请求币种和共享订单模型的具体指针。`GET /health` 及其外部响应/模型原样保留，不能因为其他共享依赖变化而产生 finding。

### 商品分页：线上编码与字段保证

旧查询 `?tags=red&tags=sale&pageSize=80` 同时暴露两类不同问题：重复键数组编码与新的逗号拼接方式可能不兼容，80 也超过新的 pageSize=50 上限。脚本分别要求序列化潜在风险和数值收紧 breaking。新增的 `includeArchived` 是可选参数，旧请求可以继续省略，应保持 non-breaking。

依赖 `X-Next-Cursor` 的翻页客户端可能因响应头移除而停止继续取页。商品的 `sku` 属性定义虽然仍在，但从 required 中移除后，列表内嵌商品和详情都可以缺少它；旧客户端直接读取非空 sku 的假设不再有保证，两处都应有 breaking。参数最大值应定位到 `parameters/catalog.json`；合成的 requiredness 或 serialization 位置使用可追溯的原字段/最近祖先，不伪造不存在的源码属性。健康检查保持不变。

### 批处理：媒体迁移不能抵消旧入口退出

旧 `POST /jobs` 允许无 body，也接受 NDJSON；JSON body 最多容纳 100 个任务。候选要求 body、移除 NDJSON、新增 CBOR，并将 JSON 任务上限降到 25。因此无 body 调用、旧媒体调用和一次提交 30 个任务分别存在独立的拒绝反例。新增媒体是 non-breaking，不会消除旧媒体删除的 breaking。

客户端原本按 202 处理提交成功，候选改为 201，应同时保留成功状态移除和新增两条 finding。轮询出现 `paused`、结果允许空数组或多达 1000 条，都扩大旧客户端可能收到的输出集合；旧穷举状态机、直接读取 `results[0]` 或按 100 条限制处理的程序需要复核。响应范围扩大按响应方向给潜在风险，不能套用请求扩容的安全结论。`GET /health` 是独立控制。

### 多租户身份：资格、凭据位置与 SDK 分开看

旧 `GET /members` 可能省略租户 header、用重复键传 roles，或仅持有 API key。候选要求 `X-Tenant-Id`、调整数组编码、重命名 operationId，并撤销该操作的 API-key 认证替代。重新生成 SDK 后方法名可能变化，即使 HTTP 路径仍在，也需要保守提示。

邀请端点还增加 `members:invite` scope，并不再接受 role=owner。原 token 或旧角色各自构成独立反例。会话撤销则把 API key 从 header `X-Tenant-Key` 改为 cookie `tenant_token`，位置和名称都要检出；不能只比较 security requirement 中的方案名称是否相同。匿名 `GET /health` 的显式安全设置和响应不变，不能继承其他操作的风险。

### 多媒体资产：声明值与实际字节是两层验证

旧原始字节上传不再被候选媒体清单接受；旧 multipart 缺少 checksum、声明大小为 8 MiB、文件名长 180 字符或有 15 个标签，也分别不满足新要求。导入操作新增 body 必填，详情不再保证 `downloadUrl`，状态新增 `quarantined`，这些 REST 结构变化有独立标签。

`sizeBytes` 是 Schema 中明确建模的数字字段，10 MiB→2 MiB 的 finding 只证明声明值收紧，不能证明文件实际大小或声明与字节一致。文件 part 的 `encoding.contentType` 变化和 binary 语义仍需真实 multipart 请求、网关及服务端校验。预期保留 `MEDIA_ENCODING_NOT_ANALYSED`、`SCHEMA_KEYWORD_PARTIAL`，不能仅凭八条 finding 把整个上传链路标成 complete。健康检查不应变化。

### IoT：两层批量边界、递归与引用相邻约束

旧遥测一次可提交 11 个批次，或一个批次带 501 个采样点；候选分别限制为 10 和 500。`mode=event`、电量 95%、配置采样间隔 1800 秒也各自存在旧合法、新拒绝的例子，应在深层数组和独立配置操作位置检出。

测量基础 Schema 最大值为 125，候选在 3.1 `$ref` 旁增加 maximum=80。旧 `sample.value=100` 因两个约束共同生效而失效，不能忽略 ref 或用普通对象覆盖相邻约束。响应新增 `degraded` 需要状态穷举复核；配置移除 HTTP delivery 分支有具体业务反例，但通用 oneOf 包含关系只给保守提示。`RECURSIVE_REFERENCE`、`SCHEMA_COMPOSITION_PARTIAL` 明确递归树和组合尚未完整证明；健康检查不引用这些模型。

### 兼容演进：变化多也可以没有 breaking

这组用于发现误报。OpenAPI 3.0 的 string+nullable 迁为 3.1 的 string/null 集合后，旧字符串与 null 仍应有效；integer `[1,99]` 改为 `(0,100)` 接受相同的整数，1、99 仍有效，0、100 仍无效。这些控制位置不应生成 finding。

请求状态枚举扩张、可选 cursor、新增可选 clientReference、备注上限放宽和 customerId 取消必填都保留原合法请求。其中 clientReference 加在原本关闭额外属性的请求对象上，不应把“新增可选属性一定安全”推广到原本开放且接受任意同名值的对象。响应已有 status 改为必需则缩小允许输出集合，增强旧客户端保证。六条预期全部 non-breaking；健康检查和两处 nullable、整数边界控制必须安静。

### 合作伙伴通知：REST finding 之外还有待验证区域

旧注册请求可能缺少 region 或 deliveryMode，候选变为必填；旧回执按字符串 deliveryId 解码、只识别两个状态和 email/http target，候选整数 id、新状态和 queue 分支分别需要确定性或保守提示。未变的伙伴查询 `GET /partners/{partnerId}` 和健康检查用于防止变更传播过头。

这次发布同时修改出站事件的 orderId 类型、增加必填 eventVersion、改变 callback URL 表达式并迁移 servers 到 `/v2`。它们可能影响伙伴接收器、签名或部署路由，但当前 REST 规则不分析这些兼容性，不能因没有相应 breaking finding 就判定安全。预期明确包含 `WEBHOOKS_NOT_ANALYSED`、`CALLBACKS_NOT_ANALYSED`、`SERVERS_NOT_ANALYSED`、`SCHEMA_COMPOSITION_PARTIAL`。需要另用接收器契约测试、旧路由验证和真实通知请求复核。

## 共享断言机制

[复杂场景入口](../scripts/scenarios-v13.mjs)与[20 个固定案例](./v1.3-acceptance-cases.md)共用[验收执行器](../scripts/lib/acceptance-suite.mjs)，保留各自清单和预期。复杂场景按清单固定顺序执行，关键断言包括：

1. **独立标签**：比较精确 `ruleId + severity + location` 多重集合，以及从清单标签单独计算的摘要计数；不是让多个入口彼此相同就视为规则正确。
2. **来源与控制**：核对指定原文件/JSON Pointer，检查未变位置没有 finding；对报告中的实际依赖逐一按提供文本重新计算 SHA-256，并逆序提供文件清单验证指纹与语义不变。
3. **三个入口**：同一输入分别调用 Core、HTTP API 和 CLI，比较输入/策略身份、finding 证据、摘要、得分、coverage；仅排除 ID、时间等非语义字段，并按 JSON 语义处理可选字段。
4. **独立门禁**：默认按清单中的 breaking 标签预期 CLI 退出 2 或 0；另以 `--fail-on never --fail-on-incomplete` 按预期 coverage 判断是否退出 2，确认门禁不会改写报告。
5. **持久化与导出**：核对历史读取、Markdown/HTML 中的 finding、coverage、策略和指定来源；随后重启同一临时分析服务，逐份核对历史恢复后的语义内容。

`complete` 表示当前检查配置未发现已知覆盖警告，不是完整语义证明；partial 的已知告警不能隐藏，旧报告缺失 coverage 也不能推断为 complete。门禁因此有两条独立轴：例如 complete 的电商 breaking 默认退出 2，但关闭等级门禁后退出 0；partial 的 multipart 即使关闭等级门禁，显式 incomplete 门禁仍应退出 2。

这套测试不调用真实模型，不执行浏览器目录选择，不验证真实业务后端接收行为、全部客户端实现、生产部署或性能。其通过结果只支持这些固定输入与断言，不代表真实 API 数据集 precision/recall，也不意味着通用 oneOf、递归、二进制或异步通知语义已经实现。运行结果应保留原始输出，并与 [V1.3 支持边界](./v1.3-upgrade.md)一起阅读。
