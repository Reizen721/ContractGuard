# V1.8：内置 Agent、调用方迁移与项目已有测试

V1.8 把原来分开的契约审查、调用方源码重放和真实项目测试接入同一个任务。选择已登记项目后，系统读取一次本地快照，执行必要检查，保存调用方报告与项目测试结果；可选模型根据已有证据选择允许的下一步，并给出有引用的迁移建议。

调用方 AST 重放仍保留 V1.7 的范围。新增的项目测试会使用 Node.js 或 Vitest **实际执行所选测试文件**。两种证据分别标识为 `bounded-typescript-replay` 和 `project-test-execution`；报告不把它们混称为完整项目或生产验证。

## 1. 直接运行

在仓库目录打开 PowerShell，首次升级先更新依赖并构建：

```powershell
pnpm install --frozen-lockfile
pnpm build
pnpm plugin:prepare
```

运行合成订单迁移演示：

```powershell
.\start-contractguard.bat --projects .\fixtures\project-tests\demo-registry.json --no-ai
```

进入 `http://127.0.0.1:8080/`，选择 **Agent 审查 → 材料来源：已登记项目与测试**，选择订单迁移项目，再点“开始审查”。无需把新旧响应正文逐次复制到网页。已有测试依次检查原始代码对基线数据、原始代码对候选数据、候选补丁对候选数据的行为。

若已有服务占用 8080，请在原窗口正常停止后重启，或增加 `--port 18082` 使用另一个端口。插件必须连接到同一个服务地址。`--check --projects ... --no-ai` 只检查启动与注册表，不运行项目测试。

本轮公开项目对照集使用独立注册表：

```powershell
.\start-contractguard.bat --projects .\fixtures\project-tests\registry.json --no-ai
```

它包含固定版本 `openapi-fetch` 的六个受控场景。源码、已有断言、变异适配和许可证的边界见 [真实项目对照记录](v1.8-benchmark.md)。这些是公开项目上的受控变异，不是六起真实历史事故。

## 2. 内置模型现在能做什么

已有五项必要检查继续执行：两侧规范校验、oasdiff breaking/changelog、原生分析。提交 `caller` 后，`caller-analysis` 成为必要步骤；选择登记项目后，`project-tests` 成为必要步骤，且在调用方分析之后运行。模型不能在必要步骤完成前结束，也不能用建议替换原始风险判定。

`workflow` 是不调用模型的固定流程。`llm` 使用服务端已配置的模型（包括 DeepSeek）选择检查顺序，接收检查状态、计数、证据 ID 和有限位置说明。原始源码、响应正文、完整补丁和原始测试输出不送入内置规划模型。外部云端 Agent 自行读取的材料及 MCP 返回仍可能进入该宿主的模型服务。

已有 DeepSeek 配置可以沿用，启动时移除 `--no-ai`，再在页面明确选择“LLM 自主编排”。密钥仍在本机启动器的隐藏输入中填写，或由原有服务端配置引用环境变量；不要写进项目注册表或 MCP 参数。首次加载 V1.8 后需重启 API 和刷新宿主插件。

## 3. 如何复用自己的项目

把注册表保存到 `config/projects.local.json`（已被 Git 忽略），根目录可以相对这个文件指定。只登记自己已经信任、允许执行的项目测试。下面展示结构，路径应替换为实际项目文件：

```json
{
  "schemaVersion": 1,
  "projects": [{
    "id": "orders-migration",
    "label": "订单调用方迁移",
    "root": "../../my-orders-client",
    "include": ["src", "test", "package.json"],
    "baseline": "contracts/baseline.json",
    "candidate": "contracts/candidate.json",
    "caller": {
      "files": ["src/orders.ts"],
      "fixtureScenarios": [{
        "id": "order-label",
        "file": "src/orders.ts",
        "exportName": "orderLabel",
        "operation": {"method": "GET", "path": "/orders/current"},
        "baselineResponse": {"status": 200, "bodyFile": "test/fixtures/old-response.json"},
        "candidateResponse": {"status": 200, "bodyFile": "test/fixtures/new-response.json"},
        "expectedFile": "test/fixtures/expected-label.json"
      }],
      "fieldRenames": "test/field-renames.json"
    },
    "tests": {
      "trusted": true,
      "runner": "vitest",
      "files": ["test/orders.test.ts"],
      "timeoutMs": 30000,
      "baseline": [{"target": "test/fixtures/response.json", "source": "test/fixtures/old-response.json"}],
      "candidate": [{"target": "test/fixtures/response.json", "source": "test/fixtures/new-response.json"}]
    }
  }]
}
```

`fixtureScenarios` 从已有 JSON fixture 读取响应和期望，自动组装 V1.7 输入；也可使用 `scenarios` 文件，二者不能同时填写。`caller` 整块可省略，已有项目测试仍可单独运行。没有 AST 场景或不支持的客户端封装保持未知；不会要求为了取得“通过”而改写业务代码。

测试适配器不会自动猜测项目如何模拟后端。已有测试应从指定 provider fixture 读取响应，或使用项目自己已有的 mock/transport helper。`baseline` / `candidate` 覆盖项只在临时副本替换明确登记的 JSON 响应文件；测试文件、源码、配置和已声明的期望文件受保护。字段语义映射仍需人确认，不根据字段相似度猜测。

`node-test` 使用固定 Node 测试命令，支持 Node 可剥离类型的 TypeScript；不等同于完整 TypeScript 编译器。`vitest` 使用项目模块依赖的固定版本运行器，可选 `tests.config` 引用已纳入快照的可信 Vitest 配置。额外依赖须已安装；可以用 `tests.dependencyDirectory` 显式引用项目内已有依赖目录，ContractGuard 不执行安装脚本。共享依赖目录不是写入隔离。

启动自己的注册表：

```powershell
.\start-contractguard.bat --projects .\config\projects.local.json
```

其他启动方式可使用进程环境变量 `CONTRACTGUARD_PROJECT_CONFIG` 指向注册表。HTTP 和 MCP 只接受登记的 `projectId`，不会接收用户提供的服务器路径、shell 命令或测试参数。

只用终端时，可以运行项目审查命令。它组合原生契约规则、调用方分析和已有测试，不调用 LLM，也不替代内置 Agent 的完整 oasdiff 检查流程：

```powershell
pnpm contractguard review-project orders-migration --registry .\fixtures\project-tests\demo-registry.json --format json --output ..\orders-project-review.json
```

报告只写入新文件，已存在时拒绝覆盖。默认存在阻断风险或未知范围即返回退出码 `2`；仅查看演示可加 `--fail-on never`，这不会改变报告中的原始门禁。

## 4. Agent / MCP 用法

V1.8 保留之前的 18 个工具，增加 `contractguard_list_projects`，共 19 个工具。先查询项目，再提交：

```json
{"projectId": "orders-migration", "mode": "workflow"}
```

这是 `contractguard_start_review` 的参数。通过返回的 `id` 调用 `contractguard_get_review`，等待任务结束。新增 `callerChecks`、`callerPatches`、`projectTests` 分页，完整输出仍通过 `contractguard_export_review` 分块导出。任务的 `callerReview.id` 可以用原来的调用方查询工具或网页打开同一条完整源码报告。

可直接向已更新的 Agent 提出：

> 查询 ContractGuard 已登记项目，审查我指定的订单迁移项目。运行本地 workflow，等待全部必要检查完成，分别说明契约风险、AST 重放结果、项目真实测试和补丁复验结果。查询关联调用方记录，完整导出报告。保留未知范围和原始发布门禁，不修改项目源码。

也可以直接向现有 `POST /api/agent/runs` 提交相同参数。项目选择与显式契约输入互斥，不能用额外参数覆盖登记的输入和命令。

不登记项目时，仍可提交原来的契约输入并增加 `caller: {files, scenarios, fieldRenames}`。网页的“调用方迁移输入包”入口直接导入 V1.7 完整 JSON，或载入内置示例，自动把两侧契约和调用方材料一起交给内置 Agent。这种输入只运行 AST 分析，不会凭空产生项目真实测试证据。

## 5. 结果如何判读

| 证据 | 可以说明什么 |
| --- | --- |
| Caller `verified` | 候选字段补丁通过已提交场景的有限语法重放 |
| Project `regression` | 已有测试在基线通过，在候选下失败，且执行的测试身份一致 |
| Project `invalid-baseline` | 基线已经失败，不能当作候选新引入的回归 |
| Project `inconclusive` | 超时、取消、无有效测试、报告不完整或执行集合不一致等，证据不足 |
| Project `patchStatus: verified` | 原回归已复现，同一组已有测试在补丁副本上通过 |
| Agent `blocked` / `review` | 综合静态规则与所有提交证据后的原始发布结论；补丁通过不自动放行 |

报告保存项目快照指纹、测试身份指纹、运行器、文件清单、阶段计数、退出码、耗时和有界输出。它有助于复核与复现，不能证明未选中的测试、未访问的路径或生产调用全部安全。报告中的耗时也不是人工审查耗时。

## 6. 执行和数据边界

- 只对本机明确登记为 `trusted: true` 的项目运行测试，默认没有登记项目；模型无权登记或扩展权限。
- 源文件进入独立快照，拒绝越界路径、符号链接、大小写歧义和超预算输入；不采集 `.env`、`.git` 或依赖目录。
- 普通测试子进程**不是操作系统安全沙箱**。可信测试代码仍可能访问本机其他文件或网络；不能用此功能执行不可信仓库，也不能把副本称为系统级隔离。
- 子进程不继承模型密钥、`NODE_OPTIONS` 或任意父环境；命令和参数由固定适配器构造，设置超时、输出限制和取消终止。测试自身读取的资料仍可能出现在输出中。
- 注册表、完整源码报告与测试输出按项目资料管理；内置模型只获得受限摘要。调用方报告与 Agent 历史可跨重启读取，未完成任务仍按原有规则标记中断。
- 没有自动安装依赖、启动真实业务服务、创建 PR、应用补丁到原项目或自动发布。真实模型、Docker、其他系统等是否经过本轮验收，以[验证记录](verification.md)为准。

## 7. 可复现验证

`pnpm check` 包含 V1.8 协议/服务/真实工具集成；其中模型调度响应由受控适配器提供，不冒充真实云端推理。公开项目对照可单独运行 `pnpm benchmark:v18`。两类验证分别记录：前者验证完整产品流程，后者展示在真实上游测试中哪些变化会被发现、哪些仍未覆盖。

本轮不使用工具数量、合成测试数量或少量变异结果宣称领先竞品。比较结论和方法见[基准文档](v1.8-benchmark.md)。

### 可选：真实 DeepSeek 验收

服务端配置 DeepSeek，并使用上述订单演示注册表启动服务后，可运行以下命令。它会实际调用已配置的云模型，**不包含在 `pnpm check` 中**；脚本不接收或读取 API Key。

```powershell
pnpm acceptance:v18:deepseek --api-url http://127.0.0.1:8080 --output ..\contractguard-live-evidence
```

该脚本通过 MCP 提交 `llm` 任务，检查必要动作、调用方历史、真实项目三阶段测试、证据引用、分页及完整导出，再运行一条不调用模型的 `workflow` 对照。输出目录必须不存在。订单候选本来存在回归，因此最终 `blocked` 是预期结果。

若验收客户端中断，先查询保存的任务状态，不要直接重复付费提交。用新的输出目录及 `--resume-run <已保存的任务ID>` 继续核对已有任务；该选项不会创建新的 LLM 任务，仍会创建一条本地固定流程对照。

已执行的真实模型结果、修正过程和文字质量边界见[DeepSeek 专项验收记录](v1.8-deepseek-acceptance.md)。
