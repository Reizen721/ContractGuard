# V1.4 与 oasdiff / OpenAPI-diff 的能力范围对照

本文是 V1.4 的静态引擎与额外样例证据实验，不是当前各产品的完整功能比较。MCP、AI 审查及商业产品的更新情况见[2026-11-02 产品定位与竞品核查](contractguard-mcp-landscape.md)。

验证日期：2026-11-02。执行环境：Windows x64、Node.js 24.21.0、OpenJDK 23.0.2。四个预先标注的合成案例均符合预期。

本次结果支持一个具体结论：**ContractGuard 可以在静态契约检查之外，用调用方提供的样例和约束发现该样例中的回归，并区分哪些已提交交互仍然满足约束。** 它不证明 ContractGuard 的规则覆盖、准确率、性能或成熟度超过另外两个工具，更不支持“全面远超”的表述。

## 对照方法

三个引擎收到相同的 OpenAPI 3.0.4 文件。ContractGuard 另外收到调用方样例 JSON；oasdiff 和 OpenAPI-diff 只运行各自的静态比较命令。这是新增证据带来的能力范围差异，不能把两个静态工具没有读取样例的结果计为漏报。

输入和预期保存在 [案例清单](../fixtures/engine-comparison/cases.json)。四个案例使用两个自包含契约文件，不依赖远程引用、数据库、实际业务服务或 LLM。案例在运行前固定，正常对照、缺失证据和已知破坏均包含在内。

| 案例 | ContractGuard 静态结果 | oasdiff 静态结果 | OpenAPI-diff 静态结果 | ContractGuard 调用方结果 |
| --- | --- | --- | --- | --- |
| 规范完全相同，候选响应样例缺少调用方必需的 receiptUrl | 0 变更 | 空数组；门禁退出 0 | no_changes；门禁退出 0 | 1 项回归；blocked |
| quantity 最小值从 1 提高到 2 | 1 项 breaking | 1 项 ERR；门禁退出 1 | incompatible；门禁退出 1 | quantity=1 回归、quantity=5 通过；blocked |
| 规范完全相同，前后样例均满足调用方约束 | 0 变更 | 空数组；门禁退出 0 | no_changes；门禁退出 0 | 1 项样例通过；pass |
| 规范完全相同，仅提交基线响应样例 | 0 变更 | 空数组；门禁退出 0 | no_changes；门禁退出 0 | 1 项证据不足；review |

在第一个案例中，提供方规范将 `receiptUrl` 声明为可选字段。基线和候选样例都符合提供方规范，但调用方自己的约束要求该字段存在。ContractGuard 的失败证据是 `REQUIRED_PROPERTY`，位置为 `/response/expectation/receiptUrl`。静态规范没有变化，因此三个静态引擎报告无变化均是正确的。

第二个案例验证共同能力和调用方细分：三者都识别了请求约束收紧。ContractGuard 的附加检查仅说明提交的单件购买样例受影响、五件购买样例仍然满足该约束；不能据此推断两个真实应用的全部调用情况。

## 复现

先构建当前 ContractGuard 源码，并自行准备所需版本的 oasdiff 可执行文件、OpenAPI-diff JAR 和 Java。比较脚本不会下载、安装或更新工具。

从仓库根目录运行，工具路径可替换为自己的位置：

```powershell
pnpm.cmd build
node scripts/compare-engines-v14.mjs --oasdiff ../ContractGuard-benchmark-tools/oasdiff.exe --openapi-diff-jar ../ContractGuard-benchmark-tools/openapi-diff-cli-2.1.7-all.jar --output ../ContractGuard-v1.4-engine-comparison
```

实现位于 [compare-engines-v14.mjs](../scripts/compare-engines-v14.mjs)。它按案例清单依次运行，通过独立参数调用子进程，不经过 shell 拼接；每次调用限制为 30 秒。固定样例没有外部引用，oasdiff 另显式禁用外部引用，使用空配置文件并清除子进程的 `OASDIFF_*` 环境覆盖。

每组实际命令等价于：

```text
oasdiff breaking <baseline> <candidate> --format json --fail-on ERR --allow-external-refs=false --config <empty-config>
java -jar <openapi-diff-2.1.7-all.jar> <baseline> <candidate> --state
java -jar <openapi-diff-2.1.7-all.jar> <baseline> <candidate> --fail-on-incompatible
```

ContractGuard 直接调用构建后的 `analyzeRelease(baseline, candidate, { consumerEvidence })`。静态 `summary` 与 `consumerImpact` 分开保存；调用方失败不会改写静态分数或兼容标记。

**OpenAPI-diff 2.1.7 的状态和门禁分两次执行。** 本次观察到 `--state` 输出状态后返回 0，即使同一命令加上 `--fail-on-incompatible` 也不会得到预期的破坏退出码。脚本因此独立运行状态查询与门禁命令，保留各自退出码，不把状态命令的 0 解读为兼容。

所有预期符合时比较脚本退出 0；任何结果或退出码不符时退出 1。这里比较脚本的退出码表示“是否符合预设案例结果”，不表示这些 API 变更是否可以发布。

## 保留的证据

输出目录包含：

- `results.json`：工具版本、执行文件指纹、运行环境、案例清单和输入文件指纹、静态与调用方结果、每项预期是否满足。
- 每个案例的 `contractguard.json`：完整规则结果、调用方检查、失败路径、负责人和迁移任务。
- 每次官方工具调用的 `*.command.json`、`*.stdout.txt` 和 `*.stderr.txt`：实际参数、退出码及原始输出。
- `README.md`：本次运行的简表。

本次实际输出位于仓库旁的 `ContractGuard-v1.4-engine-comparison` 目录。公开仓库提供输入与运行脚本；未把本机绝对路径和第三方二进制发布进仓库。

## 这次没有验证什么

只有四个主动构造的案例，并非真实企业 API 历史语料。没有测量误报率、漏报率、吞吐、内存、多文件场景的相对表现，也没有穷举 OpenAPI 或 JSON Schema。没有分析两个工具的所有扩展、插件、托管服务和周边生态。

调用方身份、负责人、期望和样例均由输入声明；系统没有扫描实际客户端代码，也没有证明样例来自线上服务。通过仅限已提交样例和已实现的约束。缺少候选样例必须保持待确认，不能自动生成一个“通过”样例来替代证据。

因此，当前更合适的产品描述是：**一个把静态 API 契约差异、调用方样例验证和迁移证据串联起来的本地工作台。** 下一轮更广泛的比较应采用真实版本历史，事先标注预期，公平运行同一类输入，并独立统计各工具的正确、错误和无法判定结果。
