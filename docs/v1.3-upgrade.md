# V1.3：本地多文件契约与分析范围

V1.3 面向一个常见场景：API 的入口文件、模型和公共响应分开维护，但希望在本机完成兼容性评审。它增加显式文件包、OpenAPI 3.0/3.1 方言处理和独立的未覆盖提示，不增加远程文件抓取、通用 Schema 求解或生产请求回放。

## 1. 升级与首次运行

停止旧服务后，在项目目录执行：

```powershell
pnpm.cmd install --frozen-lockfile
pnpm.cmd check
.\start-contractguard.bat
```

打开 `http://localhost:8080` 并刷新页面。已有分析和 V1.2 AI 解读仍可读取；旧报告没有 `coverage` 时标为“未记录”，不能自动推断已经完整分析。升级前可在服务停止后备份 `CONTRACTGUARD_DATA_DIR` 指定的数据目录；不要用源码包覆盖本机历史。

## 2. Web：目录导入与多文件演示

最快的验收路径是点击“载入多文件示例”，然后运行兼容性分析。示例比较两份 Order 契约，包含跨文件模型、3.0→3.1 的写法变化和需要人工评审的 webhook 范围。

自己的文件按如下组织即可：

```text
api-contract/
  openapi.yaml
  schemas/
    order.yaml
```

在每一侧切到“多文件契约”，选择目录并指定 `openapi.yaml` 为入口。目录导入去掉所选目录的公共前缀，保留 `schemas/order.yaml` 等包内相对路径。浏览器兼容性不同，若目录选择不可用，可使用同目录多文件选择；该方式只保留文件名，嵌套引用应使用目录导入，重名文件会被拒绝。

文件清单和预览用于核对内容，包模式不把只读预览伪装成可编辑入口。需要修改时先在本地编辑，再重新导入；切回文本、清空或载入其他示例会作废正在读取的旧文件。单文件粘贴仍可直接使用，不要求所有人创建文件包。

## 3. CLI：显式打开本地依赖读取

项目已附带可运行目录：`fixtures/multifile/baseline/` 和 `fixtures/multifile/candidate/`。在项目根目录运行：

```powershell
pnpm.cmd contractguard compare fixtures/multifile/baseline/openapi.yaml fixtures/multifile/candidate/openapi.yaml --bundle --format markdown --output contractguard-report.md --fail-on never
```

默认允许根目录是每个入口文件所在目录。如果入口位于子目录，而引用指向其上级的其他模块，必须显式指定允许根：

```text
--bundle --baseline-root ./released-contract --candidate-root ./proposed-contract
```

两个 root 分别约束旧、新文件树，入口本身必须位于对应 root 中。CLI 按核心解析器给出的缺失依赖逐一加载，不递归读取整棵目录，不读取无关文件。它检查真实路径边界并拒绝链接文件/越界目标；安全定位仍是本机受信任文件树，不承诺抵御同机攻击者在检查与读取之间恶意替换文件的竞态。

不传 `--bundle` 时保留原来的单文件行为，不会因为规范中出现 URL 或相对路径就擅自读取网络或磁盘。`--baseline-root`/`--candidate-root` 也必须配合 `--bundle`。

## 4. HTTP：只接收显式文件文本

`POST /api/analyses` 的 `baseline` 和 `candidate` 仍接受文本/对象，也可各自提供：

```json
{
  "kind": "bundle",
  "entry": "openapi.yaml",
  "files": [
    { "path": "openapi.yaml", "content": "openapi: 3.1.0\ninfo: {title: Example, version: '1'}\npaths: {}\n" }
  ]
}
```

两侧可以分别采用文本与包格式。`path` 是包内名称，不是服务器上的实际路径；HTTP 接口不会替调用方读取本机目录。请求必须包含引用所需文件，缺文件时返回明确错误，不创建成功历史。

每份包最多 50 个 YAML/JSON 文件、全部 content 的 UTF-8 大小合计最多 5 MiB。HTTP 还受配置的单份规范预算及整体 JSON 请求体上限约束，字符串转义会增加传输大小。核心另有结构、引用数量和深度预算；达到预算时明确拒绝，不能伪装成完整分析。

包内引用支持相对文件和 JSON Pointer 片段，例如 `./schemas/order.yaml#/properties/id`。包内 `../` 必须仍留在根目录内。不接受远程 URL、绝对/驱动器/UNC 路径、反斜杠、百分号编码文件路径、查询串、同名或大小写冲突文件。命名 anchor 与需要 `$id` 资源基址解析的包引用尚不支持，会明确拒绝；不要把“没有网络访问”理解成所有 JSON Schema URI 都已实现。

## 5. 方言与覆盖范围

规则之前增加方言感知的处理层，重点处理以下差异：

- OpenAPI 3.0 的 `nullable` 仅与显式 `type` 结合；OpenAPI 3.1 使用含 `null` 的类型集合，旧式 `nullable` 不再偷偷改变类型。
- 非 Schema 的 Reference Object 按版本只接受允许的相邻元数据；Schema 的 3.1 `$ref` 相邻约束是共同生效，不是普通对象覆盖。
- 能安全合取的简单约束归一比较，复杂组合保持明确的潜在风险/覆盖提示，不宣称实现全部包含关系。
- 未知 `jsonSchemaDialect`/`$schema`、资源标识与动态引用等会降级受影响的 Schema 比较并标明原因。

这不是完整 OpenAPI 文档校验器，也没有把 OpenAPI 3.2 或任意 JSON Schema 草案直接视为受支持版本。权威语义见 [OpenAPI 3.0.4](https://spec.openapis.org/oas/v3.0.4.html)、[OpenAPI 3.1.2](https://spec.openapis.org/oas/v3.1.2.html) 与 [JSON Schema 2020-12](https://json-schema.org/draft/2020-12/json-schema-core)。

新结果的 `coverage` 独立于分数和严重等级：

```json
{
  "status": "partial",
  "warnings": [
    {
      "code": "WEBHOOKS_NOT_ANALYSED",
      "side": "new",
      "location": "webhooks",
      "message": "Webhook sender/receiver compatibility is not analysed by this release.",
      "source": { "file": "openapi.yaml", "pointer": "#/webhooks" }
    }
  ],
  "truncated": false
}
```

`complete` 仅表示在当前已实现的检查配置中没有发现已知覆盖警告，不是完整语义支持、准确率、形式化证明或生产安全保证。`partial` 表示存在未证明/未覆盖内容；即使得分为 100、`compatible: true`，也仍需复核这些内容。告警最多保留 100 项，超限通过 `truncated` 明示，不静默隐藏。规则策略关闭某条 finding 不会消除覆盖警告。

默认 CLI 门禁保持兼容：只按 `--fail-on` 指定的严重等级失败。希望同时拦截不完整分析时，显式增加：

```powershell
pnpm.cmd contractguard compare fixtures/multifile/candidate/openapi.yaml fixtures/multifile/candidate/openapi.yaml --bundle --fail-on never --fail-on-incomplete
```

该示例没有规范差异，但 webhook 尚未分析，因此仍返回退出码 2。`--fail-on-incomplete` 与严重等级门禁相互独立；不要为让旧 CI 全绿而默认关闭全部告警。

## 6. 来源与隐私

`source.old/new.bundle` 记录入口和实际传递依赖的逐文件 SHA-256。包指纹基于排序后的依赖清单，文件选择顺序不影响结果；未使用文件不进入依赖指纹。单文件仍保留原文本字节指纹，不能要求任意等价写法有相同字节哈希。

finding 的 `sourceLocations.old/new` 在可定位时给出原文件和 JSON Pointer 片段，展示例如 `schemas/order.yaml#/properties/id/type`。合成位置无法精确对应时使用最近已知祖先，不伪造编辑器行号。Web、JSON、Markdown 和 HTML 报告均保留覆盖与来源信息。

历史不保存整份原始文件包，但 finding 的 before/after 证据可能包含契约片段，应继续按敏感数据保护。AI 仍不接收原始文件文本或完整包，仅额外获知覆盖状态、有限告警代码与数量；新解释使用 `ai-explainer-v3`，既有 v1/v2 保存结果可读取。

## 7. 复现与交付边界

```powershell
pnpm.cmd check
# 已完成构建后，单独执行V1.3跨入口回归
pnpm.cmd regression:v13
# 按编号执行20个固定场景
pnpm.cmd acceptance:v13
# 保留各案例的Core/API/CLI证据与有效分析的导出
node scripts/acceptance-v13.mjs --output-dir ../ContractGuard-v1.3-20-case-results
```

测试覆盖显式文件包/目录加载、路径边界、引用循环和预算、方言差异、覆盖警告、来源、旧历史以及三入口一致性。实际执行结果及 computer-use 桌面验收见 [验证记录](./verification.md)。

[20 个固定验收案例](./v1.3-acceptance-cases.md)给出真实输入路径、预先标注的预期和逐例 CLI 复核方法。套件依次检查三入口、历史与导出，并重启服务核对恢复；其中 16 个案例应生成分析，4 个应明确拒绝，预期拒绝不是测试失败。它们是关闭 AI 的合成回归，不代表 20 次浏览器实测或真实 API 准确率。

本版不包含远程引用下载、ZIP 解压、通用正则/组合 Schema 求解、消费者发现、webhook 兼容性裁决、流式协议或生产流量回放。未覆盖提示是待复核清单，不是这些场景已经实现的声明。

多项改动混合发布的输入见 [8 个复杂业务场景](./v1.3-complex-scenarios.md)，包括共享模型传播、身份与多租户、分页、异步批处理、上传及通知边界。构建后执行 `pnpm.cmd scenarios:v13` 可单独复现，`pnpm check` 也包含该套件。
