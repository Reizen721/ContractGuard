# V1.8：真实项目代码与已有测试的对照

本次使用一个公开开源项目 **openapi-fetch** 的真实客户端实现及已有 GET 测试，在本地引入六种预先定义的响应条件，比较固定 oasdiff、直接运行已有测试，以及 ContractGuard 内置 Agent 的审查结果。

**这是受控变异实验，不是历史故障复盘或生产准确率评估。** 上游源码和五个测试断言保持原样；变更来自明确标注的本地传输适配器。没有调用真实业务 API 或云模型。

## 复用范围与适配成本

原样复用的运行时代码为 `src/index.js`，测试为 `test/http-methods/get.test.ts` 的全部五项：请求方法、成功请求及返回、错误响应、数组响应和非 JSON 错误。原有 helper 已通过注入 fetch 函数产生本地 `Response`，不依赖真实服务器。

ContractGuard 对工作副本 helper 增加一处响应适配：读取 JSON 模式，只改变指定路径的成功响应，再交给原客户端。测试断言和客户端代码均未改动。原 helper 另存于 `upstream/helpers.ts`，可直接比较。

**基准契约是我们编写的窄范围 profile。** 原始 `get.yaml` 的 Post 类型包含必填 `id`，而成功响应 runtime 测试实际使用 `title/body/publish_date`。本次按 runtime 测试写出三份 profile，并单独保留上游 schema；不声称自动恢复了真实服务契约或复用了上游完整规范。

准备工作可客观计数为：一个注册表、六个项目条目、一份既有测试文件、一处传输适配、三份 authored 契约 profile、零个重写断言、零个手工 Caller 响应场景、零个字段改名确认映射。这个计数展示复用了多少现成材料，不表示安装零成本或节省了多少人时。

## 对照方法

1. **固定 oasdiff 1.35.0**：直接比较相同的新旧契约，保存原始 JSON、退出码、版本和执行时间。
2. **直接 Vitest**：独立启动根目录已安装的 Vitest，在两份临时源码副本中运行完全相同的上游测试；只替换指定 JSON 响应模式。这个参考路径不调用 ProjectRegistry 或 ProjectRunner，避免用被测执行器证明自身正确。
3. **ContractGuard Agent**：在独立 HTTP 服务中配置同一个注册表，仅提交 `projectId`。对照组通过真实 MCP stdio 创建任务，其余通过 HTTP。Agent 必须完成契约校验、上游检查、原生分析、调用方审查和项目测试；比较阶段退出码、五项测试的计数、保存记录和最终门禁。

配置的调用方材料是该项目实际的 `test/helpers.ts`，其导入和封装不属于有限 AST 重放范围。报告必须保留无法完整解释的状态，不能因项目测试通过就把源码重放改为通过。此组项目没有自动补丁，所以补丁结果应为 `not-proposed`，不计算修复成功率。

## 预定义场景与实际结果

| 场景 | 条件 | oasdiff 破坏条数 | 原有测试基线 → 候选 | Agent 项目测试 / 门禁 |
| --- | --- | --- | --- | --- |
| upstream-control | 响应不变 | 0 | 5 通过 → 5 通过 | pass / review |
| upstream-field-rename | 成功响应 title 改为 headline，契约同步改名 | 2 | 5 通过 → 4 通过、1 失败 | regression / blocked |
| upstream-status-change | 成功响应 200 改为 201，契约同步改变 | 1 | 5 通过 → 4 通过、1 失败 | regression / blocked |
| upstream-behavior-only | 契约未变，成功响应 title 值变更 | 0 | 5 通过 → 4 通过、1 失败 | regression / blocked |
| upstream-invalid-baseline | 基线模式本来破坏原有断言，候选恢复原值 | 0 | 4 通过、1 失败 → 5 通过 | invalid-baseline / review |
| upstream-uncovered-route | 修改一条已有测试不会访问的路径 | 0 | 5 通过 → 5 通过 | pass / review |

最后一例刻意说明覆盖边界：测试没有访问变更路径，五项通过不能证明该路径兼容。Agent 保留 review 是因为源码审查未形成完整证据，**不是因为系统自动找到了那个未访问的路径**。

## 实际结果

2026-11-02，Windows、Node.js 24.21.0、项目已安装 Vitest 3.2.4、oasdiff 1.35.0。执行 `node scripts/benchmark-v18.mjs --output ../ContractGuard-v18-benchmark-run2`，退出码 0，**六个场景全部符合预定义期望**。每个场景运行基线和候选各五项测试，独立参考与 Agent 执行的计数及退出码逐项一致：每条路径总计 60 次测试执行，其中 56 次通过、4 次预期失败，无跳过。这里不能把预期失败抹去并称为“120 项全通过”。

对照组经真实 MCP stdio → HTTP → 内置 Agent 完成；其余五组直接经 HTTP 提交。发现 19 个 MCP 工具，项目列表含六个配置条目；所有任务完成且 `plannerCalls=0`。源码 AST 审查没有为这些复杂封装制造成功场景或补丁；两项契约破坏的 caller gate 为 blocked，其余为 review。真实测试结果与未知范围同时保留。

仓库旁 `ContractGuard-v18-benchmark-run2/` 包含 `results.json`、六份完整 Agent JSON 和六份 oasdiff JSON。`results.json` 保存精确运行 ID、输入快照指纹、上游来源、阶段计数和执行时间。所保存时间是本机该轮墙钟观测，包含工具启动成本；未作为性能领先或人工节省时间的结论。

首次基准脚本尝试因 Windows 8.3 临时路径与 Vitest 路径匹配出现零测试，脚本立即失败，没有计为通过。独立参考路径改用 `realpath` 规范化后重新运行成功；首轮记录保留于 `ContractGuard-v18-benchmark-run1/failure.json`。这是基准执行路径问题，区别于候选响应产生的预期测试失败。

## 这轮能说明什么

复用项目既有断言之后，可以在复杂客户端超出有限 AST 支持时，仍记录真实测试的成功和失败；同契约行为变化也可以由这些测试暴露。提交已注册的项目 ID 能省去每次手工整理 Caller 响应、预期输出和源码文本的步骤。

这轮不能证明 ContractGuard 比 oasdiff 更懂 OpenAPI：行为条件不在规范中时，两者输入信息本来就不同。也不能证明它比直接跑 Vitest 更能发现测试失败：相同测试应得到相同结果，新增价值是把执行结果、契约风险、源码未知范围、历史和 Agent 工具流程组织在同一条可检查记录中。

目前只覆盖一个开源库、五个既有运行时测试和六组条件，未运行上游完整类型/构建/e2e 套件，没有模拟生产网络、鉴权或并发负载。下一步应扩大到实际业务客户端和历史 API 迁移，并测量未知比例、准备工作量、定位准确性和补丁被真实测试接受的比例。
