# ContractGuard 2.0 使用指南

这份指南从第一次启动开始，演示如何审查 API 变更、接入已有测试、配置 DeepSeek，以及在 Codex 等 Agent 中使用 MCP。命令均从 **ContractGuard 仓库根目录**执行，除非另有说明。

## 1. 选择入口

| 你的目的 | 建议入口 | 是否需要模型 |
| --- | --- | --- |
| 对比两份 OpenAPI，查看规则、位置和覆盖范围 | 网页契约分析或 CLI `compare` | 否 |
| 组合官方引擎、原生规则与已提供的调用方证据 | Agent 的 workflow 模式 | 否 |
| 让模型选择白名单检查、综合证据给出建议 | Agent 的 llm 模式 | 是 |
| 给一份已保存的分析生成通俗说明 | 分析结果中的 AI 解读 | 是 |
| 在日常编码 Agent 中分析、审查和查历史 | MCP 插件 | 宿主可以使用自己的模型；ContractGuard 的 workflow 不需要额外 Key |
| 验证调用方迁移是否通过已有测试 | 注册可信本地项目，再运行 Agent 审查 | workflow 即可 |

**任务已完成**表示检查流程结束，**门禁阻断**表示发现需要处理的风险，两者可以同时出现。不要把“任务完成”当作“允许上线”。

## 2. 安装和启动

### 环境准备

需要 Node.js **22.13 或更高**、pnpm **11.19.0**。Git 用于克隆和更新，也可以从 GitHub 下载源码 ZIP 后解压。

```powershell
node --version
npm.cmd --version
npm.cmd install --global pnpm@11.19.0
pnpm.cmd --version
git clone https://github.com/Reizen721/ContractGuard.git
Set-Location ContractGuard
```

如果已安装指定版本的 pnpm，可跳过安装命令。已有 Corepack 的环境也可使用 `corepack prepare pnpm@11.19.0 --activate`。Windows 更新 Node 后应重新打开终端，让 PATH 生效。

### Windows：推荐启动器

首次安装并启动无模型模式：

```powershell
.\start-contractguard.bat --install --no-ai
```

等待终端显示服务地址，打开 **http://127.0.0.1:8080**。关闭服务时在原终端按 `Ctrl+C`。

| 命令 | 用途 |
| --- | --- |
| `.\start-contractguard.bat --no-ai` | 使用已有构建启动，不需要 Key |
| `.\start-contractguard.bat --build --no-ai` | 源码更新后重新构建并启动 |
| `.\start-contractguard.bat --install --no-ai` | 按锁文件安装依赖、安装固定引擎、构建并启动 |
| `.\start-contractguard.bat --check --no-ai` | 检查运行环境和构建，不启动、不询问 Key |
| `.\start-contractguard.bat --port 18083 --no-ai` | 使用其他本地端口 |

启动器相对路径按调用时的目录解析。默认绑定本机地址；保持 `127.0.0.1` 即可。它不会自动读取 `.env` 文件。

### pnpm 方式：Windows、macOS、Linux

```bash
pnpm install --frozen-lockfile
pnpm engine:install
pnpm build
pnpm start
```

Windows PowerShell 阻止 `pnpm.ps1` 时，把上述命令中的 `pnpm` 换为 `pnpm.cmd`，无需修改全局执行策略。生产构建由同一个 API 服务提供网页；开发调试使用 `pnpm dev`，网页通常为 `http://127.0.0.1:5173`，API 为 8080。

首次依赖和引擎安装需要联网。普通分析、已安装引擎的 workflow 和本地示例测试无需云模型；你注册的测试本身是否访问网络取决于测试代码。

## 3. 跑通第一个完整示例

### 注册内置订单项目

停止已有服务，再在 PowerShell 启动：

```powershell
.\start-contractguard.bat --projects .\fixtures\project-tests\demo-registry.json --no-ai
```

直接 pnpm 启动时，PowerShell 使用：

```powershell
$env:CONTRACTGUARD_PROJECT_CONFIG = (Resolve-Path .\fixtures\project-tests\demo-registry.json).Path
pnpm.cmd start
```

macOS/Linux 使用：

```bash
CONTRACTGUARD_PROJECT_CONFIG="$PWD/fixtures/project-tests/demo-registry.json" pnpm start
```

在网页 Agent 工作区，将输入来源切换为注册项目，选择 **订单字段迁移与已有测试**（ID：`orders-migration`），选择 **workflow** 后开始审查。等待任务完成，查看执行记录、调用方迁移和项目测试；刷新后仍可从历史重新打开。

### 这个示例在验证什么

旧接口返回 `customerName`，新接口返回 `displayName`。`orderLabel()` 仍读取旧字段，`orderReference()` 只读取未改变的 `id`。注册表复用仓库内的响应 JSON、期望值和既有 Node 测试，并提供明确的字段重命名映射。

| 阶段 | 输入与代码 | 预期现象 |
| --- | --- | --- |
| baseline / 基线 | 旧响应 + 原调用代码 | 2 项通过 |
| candidate / 候选 | 新响应 + 原调用代码 | 1 项通过、1 项失败 |
| patched / 补丁 | 新响应 + 候选迁移代码 | 2 项通过 |

补丁阶段只在存在适用候选时运行。这里的通过证明选定调用与测试在候选补丁下恢复，不会清除契约中的破坏性变更。最终门禁为 `blocked` 是正确结果，原项目文件不会被改写。

单独查看普通契约对比时，可导入 [旧契约](../fixtures/petstore-v1.yaml) 和 [破坏性候选契约](../fixtures/petstore-v2-breaking.yaml)。这类分析不自动执行项目测试。调用方工作区也提供独立输入示例，结构见 [caller input](../fixtures/caller-impact/input.json)。

## 4. 接入自己的本地项目

### 先准备可复现的测试

选择一个你信任、已有测试可以在本机运行的项目，准备：

1. 旧版与候选版 OpenAPI 文件；多文件契约需要保留相对引用关系。
2. 希望检查的源码和已有 Node/Vitest 测试文件。
3. 旧、新两组响应 fixture，以及调用方自己的期望结果。期望不能随着候选响应一起改成“恰好通过”。
4. 让测试从一个固定 JSON fixture 读取响应。ContractGuard 在副本中替换这个 fixture，保持测试断言不变。
5. 如需生成字段迁移，提供明确的旧、新字段映射；不提供时仍可分析和运行测试。

工具不会猜测任意项目的 mock、登录状态、数据库或测试启动方式。首次接入可能需要你给既有测试增加一个 fixture/transport 接口；之后可以复用同一注册表。

### 新建本地注册表

把下面结构保存为 `config/projects.local.json`，按实际目录调整。该文件只用于本机，不应提交个人路径或项目资料。

```json
{
  "schemaVersion": 1,
  "projects": [{
    "id": "my-orders",
    "label": "我的订单客户端",
    "root": "../../my-orders-client",
    "include": ["src", "test", "package.json"],
    "baseline": "contracts/baseline.json",
    "candidate": "contracts/candidate.json",
    "caller": {
      "files": ["src/orders.ts"],
      "fixtureScenarios": [{
        "id": "order-label",
        "file": "src/orders.ts",
        "exportName": "orderLabel",
        "operation": {"method": "GET", "path": "/orders/current"},
        "baselineResponse": {"status": 200, "bodyFile": "test/fixtures/old-response.json"},
        "candidateResponse": {"status": 200, "bodyFile": "test/fixtures/new-response.json"},
        "expectedFile": "test/fixtures/expected-label.json"
      }],
      "fieldRenames": "test/field-renames.json"
    },
    "tests": {
      "trusted": true,
      "runner": "node-test",
      "files": ["test/orders.test.mjs"],
      "timeoutMs": 30000,
      "baseline": [{"target": "test/fixtures/response.json", "source": "test/fixtures/old-response.json"}],
      "candidate": [{"target": "test/fixtures/response.json", "source": "test/fixtures/new-response.json"}]
    }
  }]
}
```

`root` 相对于注册表文件所在目录；项目内其他路径相对于 `root`。例如上述注册表位于 `ContractGuard/config/` 时，`../../my-orders-client` 指向与 ContractGuard 同级的项目。`include` 选择要复制的源码、测试和必要资料；契约及显式声明的 fixture 由注册表按需收集。

`test/field-renames.json` 示例：

```json
[{"method":"GET","path":"/orders/current","from":"customerName","to":"displayName"}]
```

`fixtureScenarios` 直接复用 JSON 文件，减少手工粘贴响应；也可用 `caller.scenarios` 指定完整场景 JSON 文件，两种方式不同时使用。`caller` 整段可省略，此时仍运行已注册的项目测试，但不会凭空生成源码迁移。

启动并选取项目：

```powershell
.\start-contractguard.bat --projects .\config\projects.local.json --no-ai
```

服务只向网页/MCP 暴露项目 ID，不接受它们临时指定任意服务器目录或测试命令。修改注册表后重启服务，再重新选择项目。

### Node 与 Vitest 的区别

| 配置 | 使用条件 |
| --- | --- |
| `runner: "node-test"` | Node 内置测试，使用固定命令运行选定文件；支持可擦除类型的 TypeScript，不等价于完整 TS 编译器 |
| `runner: "vitest"` | 项目已有 Vitest 测试；使用固定 runner，先在该项目自行安装所需依赖 |
| `tests.config` | 可选的可信 Vitest 配置文件，例如 `vitest.config.mjs`，也应纳入 `include` |
| `tests.dependencyDirectory` | 可选的既有依赖目录，例如 `node_modules`；不会自动下载或安装依赖 |

对于前述示例，改用 Vitest 时，将 runner 改为 `vitest`，测试文件改成自己的 Vitest 文件，并按需要加入 `config`、`dependencyDirectory`。可以参考仓库中[公开项目注册表](../fixtures/project-tests/registry.json)。

测试在临时源码副本运行，但依赖目录可能共享；这是受限执行流程，**不是操作系统安全沙箱**。测试代码仍是普通 Node.js 程序，只注册可信项目。JSON overlay 只能修改允许的响应 fixture，不能改测试源码、配置或已声明的期望文件；未声明的隐藏期望值无法自动识别。

### 如何读测试结论

- `pass`：基线与候选的选定测试通过。
- `regression`：基线有效，候选出现测试回归。
- `invalid-baseline`：旧版本本身不通过，不能归因于本次变更。
- `inconclusive`：超时、空测试、全跳过、测试身份变化或其他证据不足。

`patchStatus` 单独描述补丁是否经过测试，不替代原有兼容性门禁。报告保留测试名称/跳过状态的身份检查、源文件指纹、截断后的本地输出和限制说明。

## 5. 配置 DeepSeek

### 推荐：本地隐藏输入

首次配置时复制公开示例；已有本地文件则直接编辑，不要覆盖：

```powershell
Copy-Item .\config\llm-providers.example.json .\config\llm-providers.local.json
.\start-contractguard.bat --projects .\fixtures\project-tests\demo-registry.json
```

启动器会自动找到 `config/llm-providers.local.json`，验证后在本地终端询问当前档案的 API Key。输入隐藏，按回车提交。密钥仅设置为本次服务进程环境变量，关闭该启动进程后不会保留；不要发到聊天、截图、GitHub 或前端输入框。

示例档案使用 `deepseek-cloud`，其中 `auth.secretEnv` 为 `DEEPSEEK_API_KEY`。JSON 保存变量名，不保存密钥本身。模型名称以配置文件和账号实际可用模型为准；改变模型后重启服务。不启用 AI 时使用 `--no-ai`。

### 直接使用 pnpm 的 PowerShell 用户

以下方式兼容 Windows PowerShell 5.1，不依赖不受支持的 `Read-Host -MaskInput`：

```powershell
$cgSecureKey = Read-Host 'DeepSeek API Key' -AsSecureString
$cgKeyPointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($cgSecureKey)
try {
  $env:DEEPSEEK_API_KEY = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($cgKeyPointer)
} finally {
  [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($cgKeyPointer)
  $cgSecureKey.Dispose()
}
$env:CONTRACTGUARD_LLM_CONFIG = (Resolve-Path .\config\llm-providers.local.json).Path
$env:CONTRACTGUARD_PROJECT_CONFIG = (Resolve-Path .\fixtures\project-tests\demo-registry.json).Path
pnpm.cmd start
```

这会在当前 PowerShell 进程保留变量，方便同一窗口重启。结束后执行 `Remove-Item Env:DEEPSEEK_API_KEY` 或关闭窗口。不要打印环境变量内容。

### 两种模型功能与数据范围

**AI 解读**读取已完成的分析，并保存独立解释记录；历史中可以再次查看或导出。它不改变 finding、分数和门禁。

**LLM Agent**根据有界观察选择允许的动作。契约验证、差异检查、调用方重放、项目测试和最终总结是不同步骤；必要检查不能被模型跳过。模型不能追加任意 shell 命令、注册项目或修改原源码。

内置云模型获得经过裁剪的发现、计数和证据摘要，不直接获得原始调用源码、完整响应 body、补丁全文或项目测试输出。外部 Agent 通过 MCP 读取完整报告后，是否传给宿主模型取决于该宿主；这属于另一条数据路径。

先查看结构化证据，再阅读自然语言建议。引用存在性校验不保证建议语义全部正确。云端失败、输出格式不合法或超时时会显示错误，不会静默换用另一个 Provider。

真实模型端到端验收是可选付费调用，在已启动服务上运行：

```powershell
pnpm acceptance:v18:deepseek --api-url http://127.0.0.1:8080 --output ..\contractguard-live-evidence
```

该脚本名沿用加入时的版本，仍可用于当前服务；输出目录必须不存在。它创建 LLM 任务，再运行无模型对照。如客户端中断，先查询已保存任务，使用新的输出目录和 `--resume-run <任务ID>` 继续检查，避免重复提交模型任务。历史真实结果见 [V1.8 专项记录](v1.8-deepseek-acceptance.md)，不代表 2.0 又调用过同一模型。

## 6. 在 Codex、Antigravity 或其他 Agent 中使用

### 生成本机配置

先构建并启动服务，在另一个终端运行：

```bash
pnpm plugin:prepare
```

默认连接 `http://127.0.0.1:8080`。如果实际为其他端口：

```bash
pnpm plugin:prepare --api-url http://127.0.0.1:18083
```

| 生成内容（`.tools/agent-plugin/` 下） | 用途 |
| --- | --- |
| `plugins/contractguard/` | 带运行文件和使用说明的可移动插件 |
| `mcp-config.json` | 通用 MCP 客户端配置片段 |
| `codex-config.toml` | Codex MCP 配置片段 |
| `antigravity-mcp.json` | Antigravity 配置片段 |
| `deepseek-harness.cordis.json` | DeepSeek Harness Cordis overlay 片段 |

插件不附带你的历史、模型账号或 Key，不会自行启动后台 API 服务。移动插件或更换 Node 安装路径后，重新生成本机配置，避免旧绝对路径失效。只有支持本地 stdio 的宿主能直接使用这套配置。

### 使用发布页的插件 ZIP

从 [GitHub Releases](https://github.com/Reizen721/ContractGuard/releases) 下载 `ContractGuard-Agent-Plugin-2.0.0.zip` 与 `SHA256SUMS.txt`，用 `Get-FileHash .\ContractGuard-Agent-Plugin-2.0.0.zip -Algorithm SHA256` 对照校验值后解压。压缩包只有插件，不包含完整 API 服务；仍须按前述源码启动步骤运行 ContractGuard。

在通用 MCP 宿主中合并下面配置，将路径改为解压后的实际 `server/index.cjs`：

```json
{
  "mcpServers": {
    "contractguard": {
      "command": "node",
      "args": ["C:/tools/contractguard/server/index.cjs"],
      "env": {"CONTRACTGUARD_API_URL": "http://127.0.0.1:8080"}
    }
  }
}
```

如果宿主找不到 `node`，使用本机 `node.exe` 的绝对路径。不要把 API Key 放进这段配置；它由 HTTP 服务处理。Codex 的 TOML 与 Harness 的 Cordis 格式不同，源码方式可直接生成对应片段。

### Codex

已安装 Codex CLI 时，用仓库助手注册直接 MCP 接入：

```bash
pnpm plugin:prepare --codex
```

助手会保留不同的既有配置，遇到冲突按输出提示合并。也可手动合并 `codex-config.toml`。需要使用完整插件/skill 的宿主，可导入生成的 `plugins/contractguard/` 或本地 marketplace；同一个宿主选择一种接入方式，避免重复工具。

### Antigravity 与 DeepSeek Harness

把生成片段合并进宿主当前使用的 MCP/Cordis 配置，不要用它覆盖整个文件。Antigravity 片段采用 `mcpServers`；Harness 片段包含 `@deepseek-ai/dsh-mcp-client` 的 Cordis `insert` 项，并不是通用 `mcpServers` 文件。宿主版本的配置位置可能不同，以宿主设置页面为准。重新加载工具或开新对话后检查是否出现 ContractGuard。

### 首次验证提示词

> 使用 ContractGuard 检查服务状态并列出注册项目。对 orders-migration 创建 workflow 审查，等待完成，查看调用方和项目测试证据。说明基线、候选和补丁各自发生了什么，并保留原门禁结论。不要修改项目源码。

用 DeepSeek 自主编排时把 `workflow` 改为 `llm`，前提是服务已配置可用档案。外部宿主自身的模型与 ContractGuard 服务端的模型是两项独立配置。

### 19 个工具的分工

| 类型 | 工具名（均以 `contractguard_` 开头） |
| --- | --- |
| 状态与规则 | `status`、`rules` |
| 普通契约分析 | `analyze`、`get_analysis`、`list_analyses`、`export_analysis` |
| AI 解读 | `explain_analysis` |
| 项目和 Agent | `list_projects`、`start_review`、`get_review`、`list_reviews`、`cancel_review`、`export_review` |
| 轻量 AST 调用方重放 | `review_callers`、`get_caller_review` |
| 神经符号 CEGAR 自修复 | `run_cegar`、`get_cegar_run`、`list_cegar_runs`、`export_cegar_run` |

例如 `start_review` 可传 `{"projectId":"orders-migration","mode":"workflow"}`，随后用返回的任务 ID 查询 `get_review`。调用方详情使用 `callerReviewId` 参数。大报告按工具返回的 `nextOffset` 继续读取，直到为空，不要只引用第一个分块。完整接口见 [MCP 说明](v1.6-agent-plugin.md)和[HTTP API](api-reference.md)。

## 7. CLI 与 CI 使用

### 契约对比

```bash
pnpm contractguard compare fixtures/petstore-v1.yaml fixtures/petstore-v2-breaking.yaml --format markdown --output contractguard-report.md --fail-on breaking
pnpm contractguard compare fixtures/multifile/baseline/openapi.yaml fixtures/multifile/candidate/openapi.yaml --bundle --fail-on never
```

`--bundle` 默认以各入口所在目录作为允许根目录；引用需要上溯时，显式指定 `--baseline-root` / `--candidate-root`。只读取实际引用的本地依赖，不抓取远程 URL。

输出格式包括 `table`、`json`、`markdown`、`html`。退出码 **0** 表示门禁策略通过，**1** 表示输入或执行错误，**2** 表示触发门禁。`--fail-on never` 只改变退出策略，不会从报告删除风险。

`--fail-on-incomplete` 单独阻断未完整覆盖的契约。提供 `--consumer-evidence <JSON文件>` 时，`--fail-on-consumer regression|review|never` 单独控制调用方样例门禁。将 `--write-regression-pack <新文件.json>` 加在 compare 命令后可保存带契约和样例的可移植包；使用 `verify-pack <文件>` 离线重放。包可能包含业务样例，分享前检查内容。

### 项目审查与 Agent 审查

```bash
pnpm contractguard review-project orders-migration --registry fixtures/project-tests/demo-registry.json --format json --output ../orders-project-review.json
pnpm contractguard agent fixtures/petstore-v1.yaml fixtures/petstore-v2-breaking.yaml --mode workflow --format markdown
pnpm contractguard oasdiff --help
```

`review-project` 复用原生规则、调用方和真实测试，默认 `review` 级别门禁，订单示例退出 **2** 属于预期；输出文件必须是新文件。`agent` 组合官方引擎与原生分析，CLI 任务保存到独立目录；Web/MCP 共享历史需要通过运行中的 HTTP 服务发起。`oasdiff` 是固定官方引擎 CLI 透传，并非每个参数都在网页上有对应控件。

## 8. 历史、升级与验证

同一 HTTP 服务的网页和 MCP 共用普通分析、AI 解读、Agent 任务和调用方记录。服务端 `CONTRACTGUARD_DATA_DIR` 指定存储根目录，默认 `./data/analyses`；Agent 与 caller 子目录也在其中。相对路径基于服务工作目录。备份时先停止服务，再复制整个实际数据目录和本地配置；不要只复制某份报告。

升级到 2.0 时保留这些本地文件，重新安装锁定依赖、构建并重启，随后重新生成插件配置。2.0 将自有包、引擎和插件统一为 `2.0.0`，报告的 `schemaVersion` 仍为 **1**。已完成的旧历史保留创建时版本，不被伪装成新版本结果。

回归包显式接受 **1.5.0** 和 **2.0.0**：旧 1.5.0 包保留原始 `engineVersion` 和 SHA 校验，重放结果标为当前 2.0.0；未知版本仍拒绝。此次兼容基于原生规则语义未变，不表示任意旧包都可跳版本重放。

```bash
pnpm check
pnpm versions:check
pnpm regression:v20
```

后两项已包含在 `pnpm check` 中，可单独定位版本与升级问题。默认测试不调用真实云模型。版本验收、公开项目对照及历史实测分别见 [2.0 验证](v2.0-verification.md)、[验证索引](verification.md)、[公开项目对照](v1.8-benchmark.md)、[历史真实 DeepSeek](v1.8-deepseek-acceptance.md)。

## 9. 常见问题

| 现象 | 检查与处理 |
| --- | --- |
| `node` 可用，`npm` 或 `pnpm` 不可用 | 先运行 `npm.cmd --version`；重开终端检查 PATH，安装指定 pnpm。`node.exe` 单独存在不代表 npm 安装完整 |
| `Read-Host` 没有 `MaskInput` | Windows PowerShell 5.1 使用启动器或本文的 `-AsSecureString` 方法 |
| 8080 被占用 | 停止旧服务，或 `--port 18083`；浏览器和插件都改为同一个端口 |
| 页面仍显示旧版本 | 先停止旧进程，执行 `--build` 重启，再刷新页面；已运行的 Node 进程不会自动读取新构建 |
| Agent 提示引擎未安装 | 执行 `pnpm engine:install`，确认安装成功后重试 |
| 没有注册项目 | 用 `--projects` 或 `CONTRACTGUARD_PROJECT_CONFIG` 启动，检查注册表 root 和固定测试路径 |
| LLM 不可用 | 确认未加 `--no-ai`，档案已启用、模型 ID 可用、Key 在服务进程内；仅在另一个终端设置变量无效 |
| 模型 JSON/证据校验失败 | 查看界面错误和任务记录；检查模型及超时设置。失败建议不会替换确定性结论；重试真实调用会再次计费 |
| MCP 工具连接失败 | 确认 HTTP 服务正在运行、生成配置的地址正确、Node/插件路径仍存在，并重新加载宿主 |
| 测试显示 inconclusive | 看测试输出与限制；排查基线失败、全跳过、空测试、依赖缺失、超时或测试身份变化 |
| 补丁没有生成 | 当前只支持明确映射和有限语法；不支持的代码会保留未知，不会为了输出补丁猜测改法 |
| 测试全过但门禁仍阻断 | 静态兼容风险与测试证据独立；有限样例通过无法证明所有既有调用方安全 |
